dsPIC33CK256MC005 และ peripheral ของชิป

ภายในชิปมีอะไรบ้าง และทำไมการทดลองทั้งแปดนี้จึงคุ้มค่าที่จะทำ

dsPIC33CK256MC005 เป็น Digital Signal Controller คือไมโครคอนโทรลเลอร์ 16 บิตที่มี DSP engine ทำงานได้เร็วสูงสุด 100 MIPS อักษร “MC” ย่อมาจาก Motor Control ส่วน “005” หมายถึงตัวถังแบบ 48 ขาที่มีหน่วยความจำแฟลช 256 KB และ RAM 16 KB การทดลอง Lab 01–30 ใช้ peripheral ที่ไมโครคอนโทรลเลอร์ทุกตัวมี (GPIO, UART, SPI, I2C, ADC, ไทเมอร์) และ peripheral ขนาดใหญ่อีกจำนวนหนึ่ง (DMA, CAN FD, PWM สำหรับมอเตอร์) ส่วน Lab 31–38 ครอบคลุม peripheral ที่ทำให้ชิปตระกูลนี้แตกต่างจากตระกูลอื่น peripheral ส่วนใหญ่เหล่านี้ทำงานได้โดยไม่ต้องใช้ CPU เมื่อตั้งค่าแล้วจะทำงานได้เอง

วัตถุประสงค์

  • หลังการทดลองนี้ ผู้เรียนสามารถตั้งค่าวงจรเปรียบเทียบ CMP1 โดยใช้ DAC ของมันเป็นค่าขีดเริ่ม และเลือกอินพุตหนึ่งในสี่อินพุตได้
  • หลังการทดลองนี้ ผู้เรียนสามารถอธิบายฮิสเทอรีซิส และวัดได้ว่าฮิสเทอรีซิสช่วยหยุดการสั่นกระพือของเอาต์พุตได้อย่างไร
  • หลังการทดลองนี้ ผู้เรียนสามารถส่งเอาต์พุตของวงจรเปรียบเทียบไปยังขาใดก็ได้ที่เลือกขาได้ (remappable) ด้วย PPS โดยไม่มี CPU อยู่ในเส้นทางสัญญาณ
  • หลังการทดลองนี้ ผู้เรียนสามารถนับขอบสัญญาณของวงจรเปรียบเทียบในอินเทอร์รัปต์ และใช้เป็นตัวนับความถี่ได้
  • หลังการทดลองนี้ ผู้เรียนสามารถอธิบายการทำงานของ ADC แบบการประมาณค่าแบบต่อเนื่อง (successive approximation, SAR) ได้ เพราะได้สร้างขึ้นเองจาก DAC และวงจรเปรียบเทียบ

ความรู้พื้นฐาน

วงจรเปรียบเทียบคืออะไร วงจรเปรียบเทียบแรงดันแอนะล็อก (analog comparator) มีอินพุตสองขาและเอาต์พุตหนึ่งบิต เอาต์พุตเป็น 1 เมื่ออินพุต + สูงกว่าอินพุต − และเป็น 0 ในกรณีอื่น มันคือ ADC ที่มีเพียงหนึ่งบิตพอดี แต่ให้คำตอบอย่างต่อเนื่องและเร็วมาก วงจรเปรียบเทียบของ dsPIC33CK ตอบสนองภายในประมาณ 15 ns ส่วน ADC ต้องใช้เวลาประมาณหนึ่งไมโครวินาทีต่อการสุ่มหนึ่งครั้ง และ CPU ต้องตรวจดูผลทุกค่า วงจรเปรียบเทียบจะรายงานเฉพาะเมื่อมีบางอย่างเปลี่ยนแปลงเท่านั้น

ใช้งานที่ไหน ใช้ป้องกันกระแสเกินในวงจรขับมอเตอร์และแหล่งจ่ายไฟ (วงจรเปรียบเทียบสามารถปิด PWM ได้ในระดับนาโนวินาที นานก่อนที่ซอฟต์แวร์จะสังเกตเห็น) ใช้ตรวจจับจุดตัดศูนย์ (zero crossing) ของสัญญาณ AC ใช้ทำสัญญาณเตือนแบตเตอรี่ต่ำที่ไม่กินเวลา CPU และใช้อ่านสัญญาณที่ไม่ได้มีระดับลอจิกที่สะอาด

  8. Plotter: ส่ง s ปิด Monitor แล้วเปิด Tools → Serial Plotter จะเห็นอินพุต เส้นค่าขีดเริ่ม และเอาต์พุตของวงจรเปรียบเทียบที่กระโดดไปมาระหว่าง 0 กับ 3000

1. การตั้งค่าโมดูล (cmpBegin() ใน Comparator.h) จ่ายไฟให้โมดูล ให้สัญญาณนาฬิกาจาก PLL แก่ DAC เลือกอินพุต ตั้งค่าขีดเริ่ม เปิดอินเทอร์รัปต์สำหรับขอบทั้งสองด้าน จากนั้นเปิด DAC ตัวนี้ (DACEN) และบล็อก DAC (DACON):

2. ค่าขีดเริ่มในหน่วยมิลลิโวลต์ DAC1DATH = mV × 4096 / 3300 แล้วปัดเศษ

3. การนับขอบสัญญาณ อินเทอร์รัปต์ทำงานทุกครั้งที่เอาต์พุตเปลี่ยน จึงนับขอบสัญญาณทั้งหมด และนับขอบขาขึ้นแยกไว้ต่างหาก (เอาต์พุตเป็น 1 อยู่แล้วเมื่ออินเทอร์รัปต์ทำงานหลังขอบขาขึ้น):

extern "C" void __attribute__((interrupt, no_auto_psv)) _CMP1Interrupt(void)
{
    cmpEdges++;
    if (DAC1CONLbits.CMPSTAT) cmpRises++;
    _CMP1IF = 0;
}

4. การส่งเอาต์พุตออกที่ขา รหัสเอาต์พุต PPS หมายเลข 23 คือ “CMP1” การเขียนค่านี้ลงในไบต์ RPnR ของขาใดจะเชื่อมวงจรเปรียบเทียบเข้ากับขานั้น (ดู Lab 32 สำหรับการทำงานของ PPS):

rpor[rp - 32] = on ? 23 : 0;        /* RPOR byte of pin RPn: 23 = CMP1, 0 = normal port pin */

5. การค้นหาแบบ SAR (cmpMeasureCode()) ฮิสเทอรีซิส การกลับเอาต์พุต และอินเทอร์รัปต์ จะถูกปิดระหว่างการค้นหา เพื่อไม่ให้รบกวนการค้นหา แต่ละสเต็ปจะรอ 2 µs ให้ DAC เข้าที่:

for (int8_t bit = 11; bit >= 0; bit--) {
    uint16_t trial = code | (1U << bit);
    DAC1DATH = trial;
    delayMicroseconds(2);                       /* DAC + comparator settle */
    if (DAC1CONLbits.CMPSTAT) code = trial;     /* input still above: keep the bit */
}

สิบสองครั้ง แต่ละครั้งตัดสินค่าหนึ่งบิต เริ่มจากบิตที่มีนัยสำคัญมากที่สุดไปจนถึงบิตที่มีนัยสำคัญน้อยที่สุด โดยลดช่วงที่เหลืออยู่ลงครึ่งหนึ่งทุกครั้ง

ทำไม LED จึงติด “กลับด้าน” หลังจากใช้คำสั่ง o?

USER LED ทำงานที่ลอจิก LOW (active low) คือติดเมื่อขาของมันเป็นลอจิก LOW เมื่อใช้ o เอาต์พุตของวงจรเปรียบเทียบจะขับขานั้นโดยตรง LED จึงติดเมื่อเอาต์พุตเป็น 0 คือต่ำกว่าค่าขีดเริ่ม การกลับเอาต์พุตของวงจรเปรียบเทียบด้วย p จะแก้ปัญหานี้ได้

สถานะ: คอมไพล์ผ่านที่ 100 MIPS (ทั้งแบบมีและไม่มี bootloader) ส่วนที่ 4 MIPS จะหยุดด้วย #error ตามที่ตั้งใจไว้ ในตัวจำลอง (MPLAB simulator) รีจิสเตอร์ทั้งหมดถูกตั้งค่าตามที่ตั้งใจ (DAC1CONL = 0xE002, DACCTRL1L = 0x80C0, RP36R = 23) แต่ตัวจำลองไม่มีวงจรเปรียบเทียบแอนะล็อก เอาต์พุตจึงไม่เปลี่ยนเลยในตัวจำลอง ยังไม่ได้ทดสอบกับฮาร์ดแวร์จริง

32PPS: Peripheral Pin Select (การเลือกขาให้ peripheral)

เชื่อมต่อ peripheral เข้ากับขาที่เลือกเองในขณะที่โปรแกรมทำงานอยู่ ได้แก่ ย้าย PWM จากขาหนึ่งไปอีกขาหนึ่ง ป้อนอินเทอร์รัปต์ตัวเดียวจากขาต่างๆ เชื่อม peripheral เข้าหากันภายในชิปด้วยขาเสมือน (virtual pin) และล็อกการจับคู่ขา

peripheralPPSRPORxRPINRxขาเสมือน RPV0-5IOLOCKSCCP1 PWMINT1 / INT2UART2 loop-back

วัตถุประสงค์

  • หลังจากการทดลองนี้ ผู้เรียนสามารถเชื่อมเอาต์พุตของ peripheral เข้ากับขาได้ โดยเขียนรหัสฟังก์ชันของ peripheral ลงในไบต์ RPnR ของขานั้น
  • หลังจากการทดลองนี้ ผู้เรียนสามารถเชื่อมอินพุตของ peripheral เข้ากับขาได้ โดยเขียนหมายเลข RP ของขาลงในฟิลด์ RPINR ของอินพุตนั้น
  • หลังจากการทดลองนี้ ผู้เรียนสามารถใช้ขาเสมือน RPV0–RPV5 เชื่อม peripheral สองตัวเข้าหากันภายในชิปได้ โดยไม่ต้องใช้สาย
  • หลังจากการทดลองนี้ ผู้เรียนสามารถล็อกและปลดล็อกการจับคู่ขา (IOLOCK) ได้ และอธิบายได้ว่าทำไมจึงต้องมีการล็อก
  • หลังจากการทดลองนี้ ผู้เรียนสามารถอ่านแผนผังการจับคู่ขาทั้งหมดของโปรแกรมที่กำลังทำงานอยู่ได้

ความรู้พื้นฐาน

ปัญหาที่ PPS แก้ไข ในไมโครคอนโทรลเลอร์ขนาดเล็กส่วนใหญ่ peripheral แต่ละตัวต่อตายตัวอยู่กับขาที่กำหนดไว้ เช่น UART1 TX อยู่ที่ขา X เสมอ ชิป 48 ขาที่มี UART สามตัว SPI สองตัว ไทเมอร์สี่ตัว และตัวควบคุม CAN หนึ่งตัว มีสัญญาณของ peripheral มากกว่าจำนวนขา ผู้ออกแบบจึงต้องยอมรับชุดการจัดขาแบบใดก็ตามที่ชิปมีให้ ใน dsPIC33CK สัญญาณของ peripheral แบบดิจิทัลส่วนใหญ่ไม่ได้ต่อเข้ากับขาโดยตรงเลย แต่ผ่านแผงสลับสาย (switchboard) ที่เรียกว่า Peripheral Pin Select และโปรแกรมเป็นผู้กำหนดว่าขาใดจะนำสัญญาณใด

OUTPUTS: one byte per PIN INPUTS: one byte per PERIPHERAL INPUT RPOR13 low byte = RP58R (pin RC10) RPINR18 low byte = U1RXR writes "1" = U1TX -> UART1 TX drives RC10 writes "59" -> UART1 RX listens to RP59 (RC11) peripheral outputs pins U1TX(1) OCM1(15) CMP1(23) PTGTRG24(46) ... --->[ RPnR = code ]---> RP32..RP61, RP65, RP72, RP74, RP77 pins RPn --->[ INT1R / U2RXR / ICM2R ... = n ]---> peripheral inputs virtual pins RP176..RP181 (RPV0..5): an output written there can be read back by any input

สองทิศทาง สองกฎ สำหรับเอาต์พุต รีจิสเตอร์เป็นของขา: ไบต์ RPnR ของขาบอกว่า peripheral ตัวใดเป็นผู้ขับขานั้น ดังนั้นเอาต์พุตของ peripheral หนึ่งตัวจึงขับได้หลายขาพร้อมกัน สำหรับอินพุต รีจิสเตอร์เป็นของ peripheral: INT1R, U1RXR และอื่นๆ เก็บหมายเลข RP ของขาที่จะรับฟังสัญญาณ ดังนั้น peripheral หลายตัวจึงรับฟังขาเดียวกันได้

หมายเลข RP ของชิปนี้ RP32–RP47 คือ RB0–RB15, RP48–RP61 คือ RC0–RC13 และยังมี RP65 (RD1), RP72 (RD8), RP74 (RD10), RP77 (RD13) ขา RA0–RA4 ไม่มีหมายเลข RP จึงจับคู่ใหม่ไม่ได้ RP176–RP181 คือขาเสมือน RPV0–RPV5 ขาเหล่านี้ไม่มีจุดต่อ (pad) บนตัวถังชิป มีไว้เพื่อเชื่อมเอาต์พุตของ peripheral เข้ากับอินพุตของ peripheral ภายในชิปเท่านั้น

สิ่งที่ PPS ไม่ได้ทำ PPS เพียงเชื่อมสัญญาณเท่านั้น ขายังต้องตั้งบิต TRIS (เป็น 0 สำหรับเอาต์พุต) และสำหรับขาที่มีฟังก์ชันแอนะล็อก ต้องตั้ง ANSEL = 0 ด้วย สัญญาณแอนะล็อก (ADC, อินพุตของวงจรเปรียบเทียบ) และสัญญาณความเร็วสูงบางตัว (ขา PWM1–PWM3, I2C1) ไม่ได้ผ่าน PPS แต่มีขาตายตัว

การล็อก โปรแกรมที่เผลอเขียนค่าลงในรีจิสเตอร์ RPOR อาจย้าย UART หรือ PWM ของมอเตอร์ไปยังขาอื่นได้ จึงสามารถล็อกการจับคู่ขาได้ โดย RPCON.IOLOCK = 1 จะไม่สนใจการเขียนทุกครั้งที่ลงในรีจิสเตอร์ของ PPS การปลดล็อกต้องใช้ลำดับรหัสกุญแจ (key sequence) ซึ่งฟังก์ชัน builtin ของคอมไพเลอร์ __builtin_write_RPCON(0x0000) เป็นผู้ทำให้ ส่วน __builtin_write_RPCON(0x0800) จะล็อกอีกครั้ง ในชิปนี้การล็อกไม่ใช่แบบทางเดียว สามารถปลดล็อกได้อีกในภายหลัง ตัว core เองก็ทำเช่นนี้ใน Serial.begin() และ analogWrite()

  4. อินพุต: กดปุ่ม USER: # INT1 interrupt 1 (from the USER button) ส่ง i: ตอนนี้ INT1 จะรับฟังที่ D8 (RB3) แทน แตะสายปลายลอยที่ D8 กับ GND: รูทีนอินเทอร์รัปต์ตัวเดิมจะนับ แต่มาจากขาอื่น ปุ่ม USER จะไม่มีผลแล้ว ส่ง i อีกครั้งเพื่อสลับกลับ
  5. ขาเสมือน วัดความถี่: ส่ง f PWM จะถูกจับคู่ไปที่ RPV0 ด้วย และ INT2 รับฟังที่ RPV0 เป็นเวลาหนึ่งวินาที INT2 จะนับขอบขาขึ้นและพิมพ์ค่าประมาณ 1000 Hz โดยไม่มีสายเกี่ยวข้องเลย
  6. ขาเสมือน UART: ส่ง u UART2 TX จะไปที่ RPV1 และ UART2 RX รับฟังที่ RPV1 สเก็ตช์จะส่งข้อความแล้วอ่านกลับมา: loop-back OK, with no wire on the board
  7. การล็อก: ส่ง k สเก็ตช์จะล็อก PPS ลองเปลี่ยนการจับคู่ของ D9 แล้วอ่านค่ากลับ (ไม่เปลี่ยน) จากนั้นปลดล็อก เปลี่ยนค่า (เปลี่ยนแล้ว) และคืนค่าเดิม
  8. ส่ง m อีกครั้ง: ตอนนี้แผนผังจะแสดง RPV0 <- OCM1, RPV1 <- U2TX, INT2 <- RPV0 และ U2RX <- RPV1 ด้วย

อธิบายการทำงานของโค้ด

1. การหาไบต์เอาต์พุตของขา (ppsOutReg() ใน PPS.h) รีจิสเตอร์ RPOR แต่ละตัวเก็บข้อมูลของสองขา และเรียงต่อกันโดยไม่มีช่องว่างตั้งแต่ RP32 (ไบต์ล่างของ RPOR0) ถึง RP77 ส่วนขาเสมือนตามมาใน RPOR24–26 ดังนั้นจึงใช้พอยน์เตอร์แบบไบต์ได้ (ตรวจสอบกับแอดเดรสใน linker script แล้ว):

volatile uint8_t *ppsOutReg(uint8_t rp)
{
    volatile uint8_t *base = (volatile uint8_t *)&RPOR0;
    if (rp >= 32 && rp <= 77)   return base + (rp - 32);
    if (rp >= 176 && rp <= 181) return base + 48 + (rp - 176);
    return 0;
}

2. การเขียนการจับคู่ขาโดยจัดการการล็อก ppsOutput() จะจำไว้ว่า PPS ถูกล็อกอยู่หรือไม่ ปลดล็อก เขียนค่า แล้วล็อกอีกครั้งถ้าก่อนหน้านั้นถูกล็อกอยู่ อินพุตเป็นบิตฟิลด์ที่มีชื่อใน device header (_INT1R, _U2RXR) ดังนั้น ppsInput() จึงเป็นมาโครที่ครอบการจัดการการล็อกแบบเดียวกัน:

ppsOutput(61, PPS_OCM1);        /* SCCP1 output -> RC13 (RP61)            */
ppsOutput(61, PPS_NONE);        /* RC13 back to a plain port pin          */
ppsInput(_INT1R, 60);           /* INT1 input  <- RC12 (RP60)             */

3. สัญญาณที่จะย้ายไปมา pwmBegin() ตั้งค่า SCCP1 ให้เป็น PWM 1 kHz (MOD = 0101, dual-edge แบบมีบัฟเฟอร์) loop() เปลี่ยนดิวตี้ตามค่าไซน์ยกกำลังสอง LED จึงดูเหมือนกำลังหายใจ ตัว PWM เองไม่เคยเปลี่ยน มีเพียงขาของมันเท่านั้นที่เปลี่ยน

4. การวัดผ่าน RPV0 PWM ไปที่ RPV0 ด้วย INT2 รับฟังที่ RPV0 และอินเทอร์รัปต์ INT2 เป็นผู้นับ:

ppsOutput(RPV0, PPS_OCM1);      /* the PWM also goes to RPV0 ...  */
ppsInput(_INT2R, RPV0);         /* ... and INT2 listens to RPV0   */
_INT2EP = 0; _INT2IF = 0; _INT2IE = 1;
int2Count = 0; delay(1000);     /* edges in one second = Hz */

5. UART loop-back ใช้ UART2 แบบวนตรวจสถานะ (polling ไม่ใช้อินเทอร์รัปต์): ส่งหนึ่งไบต์ รอสูงสุด 2 ms ให้ไบต์นั้นมาถึง FIFO ฝั่งรับ แล้วอ่านออกมา

33PTG: ตัวสร้างสัญญาณทริกเกอร์ (Peripheral Trigger Generator)

เขียนโปรแกรมสั้น ๆ ให้ตัวจัดลำดับการทำงาน (sequencer) ที่อยู่ภายในชิป: กะพริบ LED โดยไม่ใช้เวลาของ CPU เลย ตอบสนองต่อปุ่มกด สั่งให้ทำงานทีละรอบจาก CPU สร้างสัญญาณ 1 kHz ที่แม่นยำ และแสดงให้เห็นว่า PTG ไม่ได้รับผลกระทบจากสิ่งที่ CPU กำลังทำอยู่

peripheralPTGคิวของสเต็ปTimer0 / ตัวนับเอาต์พุต PTGTRIGอินเทอร์รัปต์ของ PTGทริกเกอร์ด้วยซอฟต์แวร์PPS

วัตถุประสงค์

  • หลังจากการทดลองนี้ ผู้เรียนสามารถอธิบายได้ว่า PTG คืออะไร และเมื่อใดที่ PTG เหมาะกว่าการใช้อินเทอร์รัปต์ของไทเมอร์
  • หลังจากการทดลองนี้ ผู้เรียนสามารถเข้ารหัสสเต็ปของ PTG (รอ วนลูป ทริกเกอร์ อินเทอร์รัปต์ กระโดด) และโหลดลงในคิวของสเต็ปได้
  • หลังจากการทดลองนี้ ผู้เรียนสามารถสร้างการหน่วงเวลาด้วยไทเมอร์ของ PTG และตัวนับรอบลูป และคำนวณความยาวของการหน่วงเวลาได้
  • หลังจากการทดลองนี้ ผู้เรียนสามารถเชื่อมเอาต์พุตของ PTG เข้ากับขาด้วย PPS และเชื่อมขาเข้ากับอินพุตของ PTG ได้
  • หลังจากการทดลองนี้ ผู้เรียนสามารถแสดงให้เห็นว่าลำดับการทำงานของ PTG ยังคงจังหวะเวลาเดิมไว้ได้ขณะที่ปิดอินเทอร์รัปต์

ความรู้พื้นฐาน

ทำไมต้องมีตัวสร้างสัญญาณทริกเกอร์ งานควบคุมหลายอย่างต้องการให้เหตุการณ์เกิดขึ้นตามลำดับที่แน่นอนและในเวลาที่แน่นอน เช่น “ที่จุดกึ่งกลางของคาบ PWM ให้รอ 300 ns แล้วสุ่มวัดกระแส A จากนั้น B แล้วอีก 2 µs ต่อมาวัดแรงดัน ทำแบบนี้แปดครั้งต่อคาบ” การทำเช่นนี้ด้วยซอฟต์แวร์ต้องใช้อินเทอร์รัปต์ (interrupt) และอินเทอร์รัปต์มีความคลาดเคลื่อนของเวลา (jitter) คือจะถูกหน่วงทุกครั้งที่มีอินเทอร์รัปต์อื่นทำงานอยู่หรือเมื่ออินเทอร์รัปต์ถูกปิด Peripheral Trigger Generator เป็นโปรเซสเซอร์ขนาดเล็กที่ทำงานนี้เพียงอย่างเดียว มีโปรแกรมของตัวเองได้สูงสุด 32 สเต็ป (step) สเต็ปละหนึ่งไบต์ มีไทเมอร์ 16 บิตสองตัว ตัวนับรอบลูปสองตัว และไทเมอร์หน่วงเวลาระหว่างสเต็ปหนึ่งตัว และส่งทริกเกอร์ (trigger) ไปยัง peripheral อื่น ๆ PTG ทำงานด้วยสัญญาณนาฬิกาของตัวเองและไม่ต้องรอ CPU เลย

+---------------- PTG ----------------+ inputs ----> | step queue PTGQUE0..15 (32 steps) | ----> trigger outputs 0..31 (ADC trigger = 12, PWM1-4 (0-3) | PTGQPTR = step now running | PPS pins = 24, 25, PPS inputs RP6/RP7 = 26, 27) SCCP4 (7) | Timer0 / Timer1 (PTGT0LIM/T1LIM) | ----> interrupts PTG0..PTG3 to the CPU CMP1 (9) | counter 0 / 1 (PTGC0LIM/C1LIM) | ADC (13) | step delay (PTGSDLIM) | INT2 pin (15) | clock = FCY / PTGDIV | +--------------------------------------+

1. โปรแกรมคืออาร์เรย์ของไบต์ ที่สร้างจากมาโคร:

const uint8_t PROG2[] = {               /* button -> 5 flashes */
    PTG_WLO(PTG_IN_INT2),               /* 0: wait for USER pressed (high -> low) */
    PTG_TRIG(PTG_OUT_PPS24),            /* 1: toggle LED */
    PTG_WAIT_T0,                        /* 2: 10 ms */
    PTG_JMPC0(2),                       /* 3: x10 = 100 ms */
    PTG_JMPC1(1),                       /* 4: x10 toggles = 5 flashes */
    PTG_IRQ(0),                         /* 5: burst done */
    PTG_JMP(0),                         /* 6 */
};

โปรแกรม 2 มีลูปซ้อนกันสองชั้น: ตัวนับ 0 สร้างการหน่วงเวลา 100 ms จากการรอ 10 ms สิบครั้ง ตัวนับ 1 ทำซ้ำ “สลับสถานะ + หน่วงเวลา” สิบครั้ง

2. การโหลดและการเริ่มทำงาน (PTG.h) ต้องปิด PTG ขณะเขียนคิว รีจิสเตอร์ของคิวแต่ละตัวเก็บได้สองสเต็ป โดยสเต็ป 0 อยู่ในไบต์ล่างของ PTGQUE0 ดังนั้นจึงใช้พอยน์เตอร์แบบไบต์เติมค่าลงไปตามลำดับได้:

ptgBegin(32);                       /* PTG clock = FCY / 32 */
PTGCSTbits.PTGTOGL = 1;             /* trigger steps toggle their output */
ptgSetTimer0Us(10000); PTGC0LIM = 24;
ptgLoad(PROG1, sizeof(PROG1));      /* volatile uint8_t *q = &PTGQUE0; q[i] = step */
ptgStart();                         /* PTGEN = 1, then PTGSTRT = 1 */

3. การเชื่อมต่อด้วย PPS: เอาต์พุต 24 → RC13 (รหัส 46 ใน RP61R) เอาต์พุต 25 → RB4 (รหัส 47 ใน RP36R) และ _INT2R = 60 เพื่อให้ INT2 — อินพุต 15 ของ PTG — ตามสถานะของปุ่ม USER

4. CPU ทำหน้าที่เพียงเฝ้าดู รูทีนอินเทอร์รัปต์ขนาดเล็กสองตัวนับอินเทอร์รัปต์ 0 และ 1 ของ PTG และ loop() พิมพ์ค่าที่นับได้ ทริกเกอร์ด้วยซอฟต์แวร์ของโปรแกรม 3 คือขอบสัญญาณ 0 → 1 ที่ PTGCST.PTGSWT

ลองทำด้วยตนเอง

  1. ง่าย ทำให้โปรแกรม 1 กะพริบที่ 5 Hz โดยเปลี่ยนเฉพาะ PTGC0LIM (ต้องใช้ค่าเท่าใด?)
  2. ง่าย ในโปรแกรม 2 เปลี่ยนจำนวนครั้งที่กะพริบเป็น 3 ครั้ง
  3. ปานกลาง เขียนโปรแกรมที่ทำให้ LED กะพริบแบบ “จังหวะหัวใจเต้น”: กะพริบสั้นสองครั้ง หยุดนาน แล้วทำซ้ำ
  4. ปานกลาง ใช้วอตช์ด็อก (watchdog) ของ PTG (PTGCON.PTGWDT) ในโปรแกรม 2 เพื่อให้เมื่อไม่มีการกดปุ่มนานเกินไปจะเกิด _PTGWDTInterrupt
  5. ท้าทาย สุ่มวัด ADC ด้วย PTG: ส่งทริกเกอร์ที่เอาต์พุต 12 (ทริกเกอร์ของ ADC) ทุก 1 ms และตั้งแหล่งทริกเกอร์ของ ADC เป็น PTG จากนั้นเปรียบเทียบจังหวะเวลาของการสุ่มวัดกับแบบที่ใช้อินเทอร์รัปต์ของไทเมอร์ ขณะที่ CPU ไม่ว่าง

ทดสอบความเข้าใจ

ทำไมจังหวะของ LED จึงไม่เปลี่ยนระหว่างการทดสอบขณะ CPU ไม่ว่าง ในขณะที่การพิมพ์ทาง Serial หยุดลง?

PTG ทำงานด้วยสัญญาณนาฬิกาของตัวเองและใช้เฉพาะไทเมอร์และตัวนับของตัวเอง ดังนั้นการที่ CPU ไม่ว่างหรือการปิดอินเทอร์รัปต์จึงไม่มีผลต่อ PTG ส่วนการพิมพ์ต้องใช้ CPU

เมื่อสัญญาณนาฬิกาของ PTG เป็น 3.125 MHz การรอด้วย PTG_WAIT_T0 หนึ่งครั้งยาวได้มากที่สุดเท่าใด?

65536 สัญญาณนาฬิกา / 3.125 MHz = 21 ms การรอที่ยาวกว่านั้นทำได้โดยใช้ตัวนับรอบลูปครอบการรอไว้

PTG_JMPC0(0) ที่มี PTGC0LIM = 24 ทำอะไร?

กระโดดกลับไปยังสเต็ป 0 จำนวน 24 ครั้ง (บวก 1 ให้ตัวนับ 0 ทุกครั้ง) จากนั้นล้างค่าตัวนับแล้วทำต่อ ดังนั้นส่วนเนื้อหาของลูปจึงทำงาน 25 ครั้ง

เมื่อใดที่ควรใช้ PTG แทนอินเทอร์รัปต์ของไทเมอร์?

เมื่อจังหวะเวลาของลำดับเหตุการณ์ต้องไม่มีความคลาดเคลื่อน (jitter): เช่น การสุ่มวัด ADC ที่ตำแหน่งที่แน่นอนในคาบ PWM การทริกเกอร์ peripheral หลายตัวตามลำดับที่กำหนดไว้ หรืองานใด ๆ ที่ต้องทำงานต่อไปได้ขณะที่ CPU ไม่ว่างหรือขณะที่ปิดอินเทอร์รัปต์

สถานะ: คอมไพล์ผ่านทั้งสองค่าสัญญาณนาฬิกาและเมื่อใช้ร่วมกับ bootloader โดยไม่มีคำเตือน ยังไม่ได้ทดสอบ: ตัวจำลอง (MPLAB simulator) ไม่ได้จำลองการทำงานของ PTG (ไม่เคยออกจากสเต็ป 0) และยังไม่ได้สร้างบอร์ดจริง คำสั่ง ? และ l แสดงตัวชี้สเต็ป ดังนั้นเมื่อใช้กับชิปจริงครั้งแรกจะเห็นได้ทันทีว่า PTG ทำงานหรือไม่

34CRC: วงจรคำนวณ CRC แบบฮาร์ดแวร์ (CRC engine)

ทำความเข้าใจว่า CRC คืออะไร และ CRC-8, CRC-16 และ CRC-32 ต่างกันอย่างไร ให้วงจร CRC engine ของชิปคำนวณค่าเหล่านี้ ตรวจสอบผลเทียบกับซอฟต์แวร์และค่าทดสอบมาตรฐาน วัดความเร็ว และนำไปใช้กับเฟรม Modbus และกับหน่วยความจำแฟลชของโปรแกรม

วัตถุประสงค์

  • หลังการทดลองนี้ ผู้เรียนสามารถอธิบายได้ว่า CRC ตรวจจับความผิดพลาดได้อย่างไร และทำไมจึงดีกว่าการบวกไบต์รวมกัน
  • หลังการทดลองนี้ ผู้เรียนสามารถอธิบาย CRC ใด ๆ ด้วยพารามิเตอร์ 6 ตัวของแบบจำลอง “Rocksoft” และตรวจสอบโค้ดที่เขียนด้วยสตริงทดสอบ “123456789” ได้
  • หลังการทดลองนี้ ผู้เรียนสามารถตั้งค่า CRC engine ของ dsPIC33CK สำหรับ CRC ขนาด 8, 16 และ 32 บิต รวมถึงแบบกลับลำดับบิต (reflected) ได้
  • หลังการทดลองนี้ ผู้เรียนสามารถเปรียบเทียบความเร็วของ engine กับวิธีทางซอฟต์แวร์ 2 วิธีได้
  • หลังการทดลองนี้ ผู้เรียนสามารถตรวจสอบเฟรม Modbus RTU และคำนวณ CRC-32 ของหน่วยความจำแฟลชของโปรแกรมได้

ความรู้พื้นฐาน

CRC คืออะไร Cyclic Redundancy Check (การตรวจสอบความซ้ำซ้อนแบบวน) มองข้อความทั้งหมดเป็นเลขฐานสองยาวหนึ่งจำนวน แล้วหารด้วยเลขคงที่ค่าหนึ่งที่เรียกว่า พหุนามตัวกำเนิด (generator polynomial) โดยใช้ XOR แทนการลบ เศษที่เหลือคือค่า CRC ฝั่งผู้ส่งต่อค่านี้ท้ายข้อความ ฝั่งผู้รับคำนวณซ้ำแล้วนำมาเปรียบเทียบ หากมีบิตผิดเพียงบิตเดียวไม่ว่าตำแหน่งใด เศษก็จะเปลี่ยนไป

ทำไมไม่บวกไบต์รวมกันเฉย ๆ ผลรวมไม่สามารถสังเกตเห็นการสลับตำแหน่งไบต์ และความผิดพลาด 2 จุดอาจหักล้างกันเองได้ CRC ที่ดีตรวจจับความผิดพลาดบิตเดียวและสองบิตได้ทุกกรณี ตรวจจับความผิดพลาดที่มีจำนวนบิตผิดเป็นเลขคี่ได้ทุกกรณี และตรวจจับความผิดพลาดแบบต่อเนื่อง (burst) ที่สั้นกว่าความยาวของ CRC ได้ทุกกรณี นี่คือเหตุผลที่ Ethernet, USB, CAN, Modbus, ไฟล์ ZIP และ serial bootloader ของบอร์ดนี้ล้วนใช้ CRC

ในฮาร์ดแวร์ CRC คือชิฟต์รีจิสเตอร์ (shift register) การหารสามารถทำทีละบิตได้ด้วยชิฟต์รีจิสเตอร์และเกต XOR จำนวนหนึ่ง วางไว้ในตำแหน่งที่พหุนามมีบิตเป็น 1

CRC-16/CCITT, polynomial x^16 + x^12 + x^5 + 1 = 0x1021 data bit in -->(XOR)-->[ register bit 0 ... 4 ]--(XOR)-->[ bit 5 ... 11 ]--(XOR)-->[ bit 12 ... 15 ]--+ ^ ^ ^ | +---------------------------------+--------------------------+-------------------+ feedback = bit 15

ในซอฟต์แวร์ งานนี้ใช้ประมาณ 10 คำสั่งต่อบิต ส่วน engine เลื่อนบิตหนึ่งบิตต่อหนึ่งรอบคำสั่ง (instruction cycle) ขณะที่ CPU เขียนไบต์ถัดไปลงใน FIFO ขนาด 16 ไบต์ของ engine ต่อไปได้

CRC engine ของ dsPIC33CK และสองเรื่องที่ต้องรู้ ผู้เรียนกำหนดความยาวพหุนาม (PLEN) ความกว้างข้อมูล (DWIDTH ในที่นี้คือ 8 บิต) พหุนาม (CRCXOR) ค่าเริ่มต้น (CRCWDAT) และลำดับบิต (LENDIAN) จากนั้นสั่งเริ่มด้วย CRCGO และเขียนไบต์ลงใน CRCDATL engine ที่ใช้ในที่นี้ (โหมด legacy) เป็นชิฟต์รีจิสเตอร์แบบ “augmented” ตามตำรา ซึ่งต่างจากนิยาม CRC ทั่วไปอยู่ 2 ประการ ทั้งสองประการพบระหว่างการทดสอบของการทดลองนี้ และ crcHw() จัดการให้แล้ว

  • ตอนท้าย ต้องเลื่อนบิตศูนย์จำนวน width บิตผ่านเข้าไปหลังข้อมูล สำหรับ CRC-16 คือไบต์ศูนย์ 2 ไบต์ สำหรับ CRC-32 คือ 4 ไบต์
  • ตอนเริ่ม ต้องแปลงค่าเริ่มต้นแบบ “direct” ที่ใช้กันทั่วไปให้เป็นค่าเริ่มต้น (seed) แบบ “indirect” ที่สอดคล้องกัน โดยเดินชิฟต์รีจิสเตอร์ย้อนกลับ width สเต็ป สำหรับ CRC-16/CCITT ค่า 0xFFFF จะกลายเป็น 0x84CF

รีจิสเตอร์จะเลื่อนบิตโดยเริ่มจาก MSB เสมอ ดังนั้นสำหรับ CRC แบบกลับลำดับบิต ข้อมูลจะถูกป้อนเข้าโดยเริ่มจาก LSB (LENDIAN = 1) และผลลัพธ์จะถูกกลับลำดับบิตในตอนท้าย

Modbus: ส่ง m สเก็ตช์จะสร้างคำขอ Modbus RTU “อ่าน holding register 2 ตัวจาก slave 1” แล้วต่อท้ายด้วย CRC-16/MODBUS (ไบต์ต่ำก่อน) ได้เป็น 01 03 00 00 00 02 C4 0B การตรวจสอบฝั่งผู้รับจะแสดง GOOD จากนั้นจะกลับค่าบิตหนึ่งบิต เหมือนถูกรบกวนระหว่างทางบนสาย และการตรวจสอบจะแสดง BAD Lab 24 ใช้ CRC แบบเดียวกันนี้
  4. ลายนิ้วมือของเฟิร์มแวร์ (fingerprint): ส่ง f engine จะคำนวณ CRC-32 ของสเก็ตช์ในหน่วยความจำแฟลชของโปรแกรม โดยอ่านคำสั่งขนาด 24 บิตแต่ละคำเป็น 3 ไบต์ เมื่อใช้ serial bootloader ช่วงข้อมูลและอัลกอริทึมนี้เป็นแบบเดียวกับที่โปรแกรมอัปโหลดใช้ตรวจสอบการอัปโหลด ดังนั้นตัวเลขจะตรงกับบรรทัด “CRC-32 0x…” ที่โปรแกรมอัปโหลดพิมพ์ออกมา ลองแก้สเก็ตช์หนึ่งบรรทัด อัปโหลดใหม่ แล้วส่ง f จะเห็นว่าลายนิ้วมือเปลี่ยนไป
  5. ข้อความของผู้เรียนเอง: พิมพ์ข้อความใดก็ได้แล้วกด Enter เช่น hello สเก็ตช์จะพิมพ์ CRC ของข้อความนั้น 4 แบบ ตรวจสอบค่าเหล่านี้ด้วยเครื่องคำนวณ CRC ออนไลน์
  6. โหมด alternate: ส่ง a engine ยังมีโหมด “alternate” (MOD = 1) ด้วย สเก็ตช์จะทดสอบว่าบนชิปของผู้เรียน โหมดนี้คำนวณ CRC แบบ direct ได้โดยไม่ต้องเติมไบต์ศูนย์หรือไม่ ในตัวจำลองคำตอบคือ “ไม่ได้” บนชิปจริง ให้จดผลที่ได้ไว้

5. ค่าเริ่มต้นแบบ indirect ได้จากการเดินชิฟต์รีจิสเตอร์ย้อนกลับ เมื่อบิต 0 ของรีจิสเตอร์เป็น 1 แสดงว่าต้องเคยมีสเต็ปป้อนกลับ (feedback) เกิดขึ้น จึง XOR พหุนามออกและคืนค่าบิตบนสุด

for (uint8_t i = 0; i < width; i++) {

Deadman Timer (DMT) เป็นตัวนับขนาด 32 บิตที่นับรอบคำสั่ง (instruction cycle) ไม่ใช่นับเวลา โปรแกรมต้องเคลียร์มันด้วยรหัสกุญแจสองขั้น และต้องเคลียร์ภายในหน้าต่างเวลา (window) เท่านั้น

ดังนั้นโค้ดระหว่างการเคลียร์สองครั้งต้องใช้คำสั่งอย่างน้อย DMTIVT คำสั่ง (มิฉะนั้นแสดงว่าข้ามบางอย่างไป) และอย่างมาก DMTCNT คำสั่ง (มิฉะนั้นแสดงว่าค้างหรือทำงานนานเกินไป) ลูปที่ติดค้างแต่ยังวนมาถึงจุดเคลียร์ได้ก็จะถูกจับได้ เพราะมันเคลียร์เร็วเกินไป

เหตุการณ์ DMT จะทำให้เกิดอินเทอร์รัปต์ของ DMT (เวกเตอร์ 45, IFS2.DMTIF) สเก็ตช์ (sketch) นี้บันทึกสิ่งที่เกิดขึ้นลงใน RAM ที่ค่าคงอยู่หลังรีเซ็ต (ตัวแปร persistent เหมือนใน Lab 28) แล้วรีเซ็ตชิปด้วยคำสั่ง reset หลังเริ่มทำงานใหม่ สเก็ตช์จะรายงานว่าเกิดความผิดพลาดอะไรขึ้น

Configuration word เวลาหมดเวลาและหน้าต่างเวลาไม่ใช่รีจิสเตอร์ที่เขียนค่าได้ขณะโปรแกรมทำงาน แต่เป็นconfiguration word ในหน่วยความจำแฟลช ซึ่งถูกโปรแกรมลงไปพร้อมกับสเก็ตช์

Config wordในสเก็ตช์นี้ความหมาย
DMTDISOFFDMT ปิดอยู่เมื่อรีเซ็ต โปรแกรมเปิดมันเองได้ (ON = เปิดตลอดเวลา)
DMTCNTL/Hจำนวนคำสั่งเท่ากับ 2 s (200 000 000 ที่ 100 MIPS)ค่านับของเวลาหมดเวลา (time-out)
DMTIVTL/Hจำนวนเท่ากับ 1 s (100 000 000 ที่ 100 MIPS)หน้าต่างเวลาเปิดที่ค่านับนี้

สเก็ตช์กำหนดค่าเหล่านี้ด้วย #pragma config โดยเลือกค่าให้เหมาะกับสัญญาณนาฬิกาที่เลือกไว้ ขณะทำงาน ชิปจะคัดลอกค่าเหล่านี้ไปไว้ใน DMTPSCNTL/H และ DMTPSINTVL/H และสเก็ตช์จะอ่านค่าจากรีจิสเตอร์เหล่านั้นเพื่อแสดงว่าค่าที่ถูกโปรแกรมไว้จริงคืออะไร

อัปโหลดด้วย PICkit configuration word จะถูกโปรแกรมเฉพาะเมื่ออัปโหลดด้วย PICkit เท่านั้น (Tools → Bootloader → None) serial bootloader จะไม่เขียนค่าเหล่านี้เลย เพราะค่าเหล่านี้เป็นของตัว bootloader เอง หลังอัปโหลดผ่านพอร์ตอนุกรม word ของ DMT จะยังอยู่ในสถานะถูกลบ คือ DMTCNT = DMTIVT = 0xFFFFFFFF หน้าต่างเวลาจะเปิดก็ต่อเมื่อถึงเวลาหมดเวลาพอดี และไม่สามารถเคลียร์ DMT ได้ สเก็ตช์จะตรวจพบกรณีนี้และแจ้งให้ทราบ

การต่อวงจร

ไม่ต้องต่อวงจรใด ๆ นอกจากตัวแปลง USB-serial ที่ J5 และเครื่องโปรแกรม (programmer) ที่ J4 LED ของผู้ใช้ (USER LED) จะกะพริบช้า ๆ ขณะที่ loop() ทำงาน และจะกะพริบสั้น ๆ ทุกครั้งที่เคลียร์ DMT

ขั้นตอนการทดลอง

  1. เลือก Bootloader → None และ PICkit ของคุณ อัปโหลด Lab35_DeadmanTimer แล้วเปิด Serial Monitor สถานะจะแสดง time-out DMTCNT = 200000000 instructions = 2.000 s และ window DMTIVT = 100000000 = 1.000 s (ที่ 100 MIPS) สถานะ off ถ้าเห็นค่าที่คล้าย 0xFFFFFFFF และมีคำเตือน แสดงว่า config word ไม่ได้ถูกโปรแกรม ให้อัปโหลดด้วย PICkit
  2. เริ่มการทำงาน: ส่ง d ตั้งแต่นี้ไปจะไม่สามารถหยุดมันได้ loop() จะเคลียร์มันทันทีที่หน้าต่างเวลาเปิด ประมาณวินาทีละครั้ง และ LED จะกะพริบทุกครั้งที่เคลียร์ ส่ง ? จะได้ค่าตัวนับ WINOPN และระยะเวลาระหว่างการเคลียร์สองครั้งล่าสุด (ประมาณ 1000 ms)
  3. ช้าเกินไป: ส่ง h loop() จะหยุดเคลียร์ แต่ยังทำงานต่อไป (LED ยังกะพริบอยู่) ประมาณ 1 s ต่อมา ตัวนับจะถึงค่า DMTCNT เกิดเหตุการณ์ DMT และชิปเริ่มทำงานใหม่ รายงานจะแสดง DMT EVENT ค่าตัวนับ (ประมาณเท่ากับ 2 s) และ 'h' stop clearing -> too LATE
  4. เร็วเกินไป: ส่ง d อีกครั้ง (การรีเซ็ตทำให้มันหยุดไปแล้ว) แล้วส่ง e สเก็ตช์จะเคลียร์อย่างถูกต้องหนึ่งครั้ง ซึ่งทำให้หน้าต่างเวลาปิด แล้วเคลียร์ซ้ำทันทีขณะที่หน้าต่างเวลาปิดอยู่ เหตุการณ์ DMT จะเกิดขึ้นทันที และรายงานจะแสดง too EARLY
  5. รหัสกุญแจผิด: ส่ง d แล้วตามด้วย k ขั้นแรกของรหัสกุญแจจะถูกเขียนด้วยค่าที่ผิด เหตุการณ์จะเกิดขึ้นทันที และรายงานจะแสดง BAD1 / wrong STEP1 key
  6. การนับคำสั่ง: ส่ง d แล้วตามด้วย n สเก็ตช์จะปิดอินเทอร์รัปต์ แล้วอ่านค่าตัวนับก่อนและหลังการทำงานบางอย่าง และพิมพ์ว่าแต่ละอย่างใช้กี่คำสั่ง ได้แก่ การหารแบบ long การหารแบบ float sqrtf sinf และ analogRead() ชิปนี้ไม่มีหน่วยประมวลผลจุดลอยตัว (floating point) ดังนั้นการคำนวณแบบ float จึงใช้คำสั่งมากกว่าการคำนวณแบบจำนวนเต็มมาก
  7. กด RESET DMT จะปิดอีกครั้งจนกว่าจะส่ง d ครั้งถัดไป หลังจากปิดไฟเลี้ยง ตัวนับจำนวนเหตุการณ์จะเริ่มนับใหม่จาก 0

บิตของ DMTSTAT ที่แน่นอนสำหรับความผิดพลาดแต่ละแบบคือสิ่งที่การทดลองนี้จะค้นหาบนชิปของคุณ ให้จดบันทึกค่าเหล่านี้สำหรับ h, e และ k

อธิบายการทำงานของโค้ด

1. Config word สำหรับสัญญาณนาฬิกาที่เลือก (ส่วนบนสุดของสเก็ตช์) FCY มาจากเมนู Clock ดังนั้นหน้าต่างเวลาจะเป็น 1 s และเวลาหมดเวลาจะเป็น 2 s เสมอ

#pragma config DMTDIS = OFF                 /* software switches it on */
#if FCY == 100000000UL
#pragma config DMTCNTL = 0xC200             /* 200 000 000 = 0x0BEBC200 -> 2 s */
#pragma config DMTCNTH = 0x0BEB
#pragma config DMTIVTL = 0xE100             /* 100 000 000 = 0x05F5E100 -> 1 s */
#pragma config DMTIVTH = 0x05F5
#else ...

2. เคลียร์เฉพาะภายในหน้าต่างเวลา (dmtClear() ใน DMT.h) DMTSTAT.WINOPN บอกว่าหน้าต่างเวลาเปิดอยู่หรือไม่ ดังนั้นฟังก์ชันนี้จึงไม่เคลียร์เร็วเกินไปโดยไม่ตั้งใจ

bool dmtClear()
{
    if (!DMTSTATbits.WINOPN) return false;
    DMTPRECLR = 0x4000;                 /* STEP1 = 0x40 */
    DMTCLR = 0x0008;                    /* STEP2 = 0x08 */
    return true;
}

3. การอ่านตัวนับ 32 บิตอย่างปลอดภัย ตัวนับประกอบด้วยสองส่วน ส่วนละ 16 บิต และยังนับต่อไปขณะที่กำลังอ่าน ให้อ่านส่วนบน ส่วนล่าง แล้วอ่านส่วนบนอีกครั้ง ถ้าส่วนบนเปลี่ยนไป แสดงว่าส่วนล่างวนค่ากลับ (wrap-around) ในระหว่างนั้น จึงต้องอ่านใหม่

4. เหตุการณ์ (_DMTInterrupt ลำดับความสำคัญ 7 เพื่อไม่ให้มีสิ่งใดมาขัดขวางได้) บันทึกค่าตัวนับ DMTSTAT และตัวเลขเฉพาะ (magic number) ลงในโครงสร้าง persistent ที่ตำแหน่ง 0x4F40 แล้วเรียก asm("reset") ฟังก์ชัน dmtBootCheck() ใน setup() จะพบบันทึกนี้หลังเริ่มทำงานใหม่ (RCON แสดง SWR) และฟิลด์ tag ของสเก็ตช์เองจะบอกว่าคำสั่งใดเป็นต้นเหตุ

5. การนับคำสั่ง (countOne()) ปิดอินเทอร์รัปต์ อ่านค่าตัวนับ ทำงานที่ต้องการวัด แล้วอ่านค่าอีกครั้ง ผลต่างที่ได้จะรวมคำสั่งประมาณ 10 คำสั่งที่ใช้ในการอ่านสองครั้งนั้นด้วย

ทำไมการตั้งค่า DMT ของสเก็ตช์จึงใช้ได้เฉพาะหลังอัปโหลดด้วย PICkit

เวลาหมดเวลาและหน้าต่างเวลาเป็น configuration word ซึ่ง serial bootloader เป็นเจ้าของหน้าหน่วยความจำ configuration และไม่เคยเขียนลงไป ดังนั้นหลังอัปโหลดผ่านพอร์ตอนุกรม word เหล่านี้จึงยังอยู่ในสถานะถูกลบ

สถานะ: คอมไพล์ผ่านทั้งสองความถี่สัญญาณนาฬิกาและเมื่อใช้ bootloader โดยไม่มีคำเตือน ไฟล์ hex มี config word ของ DMT ตามที่ตั้งใจไว้สำหรับแต่ละความถี่สัญญาณนาฬิกา ยังไม่ได้ทดสอบ: ตัวจำลอง (MPLAB simulator) ไม่มีแบบจำลองของ DMT (ตัวนับของมันค้างอยู่ที่ 0) และยังไม่ได้สร้างบอร์ดจริง เนื้อหานี้เขียนจาก data sheet สเก็ตช์จะพิมพ์สิ่งที่ชิปทำจริงออกมาให้เห็น

36คณิตศาสตร์ DSP: เลขจุดตรึงแบบ Q15 และหน่วย MAC

เรียนรู้รูปแบบตัวเลขที่ใช้ในการประมวลผลสัญญาณ และ DSP engine ซึ่งเป็นสิ่งที่ทำให้ชิปนี้เป็น “dsPIC” แล้ววัดความแตกต่างของฟิลเตอร์ตัวเดียวกันเมื่อเขียนด้วย float, ภาษา C ธรรมดา และเมื่อใช้หน่วย MAC จากนั้นนำไปกรองสัญญาณ วัดค่า RMS และถอดรหัสเสียงโทรศัพท์

วัตถุประสงค์

  • หลังการทดลองนี้ สามารถอ่านและเขียนตัวเลขจุดตรึง (fixed point) แบบ Q15 และคูณตัวเลขเหล่านี้ได้อย่างถูกต้อง
  • หลังการทดลองนี้ สามารถอธิบายการล้น (overflow) การวนค่ากลับ (wrap-around) และการอิ่มตัว (saturation) ได้ รวมถึงอธิบายได้ว่าบิตกันล้น (guard bits) 8 บิตของแอคคิวมูเลเตอร์ (accumulator) มีไว้เพื่ออะไร
  • หลังการทดลองนี้ สามารถใช้ฟังก์ชัน builtin สำหรับ DSP ของคอมไพเลอร์ (__builtin_mac และฟังก์ชันในกลุ่มเดียวกัน) และลูป REPEAT + MAC ที่มีการดึงข้อมูลล่วงหน้า (prefetch) ของตัวถูกดำเนินการได้
  • หลังการทดลองนี้ สามารถออกแบบฟิลเตอร์ FIR แบบผ่านต่ำ (low-pass) และนำไปใช้กับสัญญาณได้
  • หลังการทดลองนี้ สามารถตรวจวัดความแรงของความถี่หนึ่งความถี่ด้วยอัลกอริทึม Goertzel ได้

ความรู้พื้นฐาน

ทำไมไม่ใช้ float ไปเลย? ชิปนี้ไม่มีหน่วยคำนวณจุดลอยตัว (floating-point unit) การคูณ float หนึ่งครั้งเป็นการเรียกฟังก์ชันในไลบรารีที่ใช้ 30–100 คำสั่ง งานประมวลผลสัญญาณ (ฟิลเตอร์ ลูปควบคุม การควบคุมมอเตอร์) ต้องคูณเลขหลายล้านครั้งต่อวินาที จึงใช้ตัวเลขแบบจุดตรึง (fixed point) แทน ซึ่งก็คือเลขจำนวนเต็มที่ถูกตีความเป็นเศษส่วน

Q15 คือ int16_t ที่ตีความเป็น ค่า / 32768 ครอบคลุมช่วง −1 … +0.99997 โดยมีขั้นละ 0.00003

0x7FFF = +0.99997 0x4000 = +0.5 0x2000 = +0.25 0x0000 = 0 0xC000 = -0.5 0x8000 = -1.0 multiply: 0.5 x 0.5 = 0x4000 x 0x4000 = 0x10000000 (Q30) >> 15 = 0x2000 = 0.25

เมื่อนำเลข Q15 สองตัวมาคูณกันจะได้ผลลัพธ์แบบ Q30 ขนาด 32 บิต ให้เลื่อนบิตไปทางขวา 15 บิตเพื่อกลับมาเป็น Q15 ค่า +1.0 ไม่สามารถเขียนเป็น Q15 ได้ ดังนั้น −1 × −1 จึงเป็นกรณีพิเศษ

การล้น (overflow): วนค่ากลับหรือให้ค่าอิ่มตัว 0.9 + 0.9 = 1.8 ซึ่งเก็บไม่ได้ การคำนวณเลขจำนวนเต็มในภาษา C ธรรมดาจะวนค่ากลับ (wrap around) ไปเป็นเลขลบ (−0.2) ในฟิลเตอร์หรือลูปควบคุม สิ่งนี้จะเปลี่ยนค่าบวกขนาดใหญ่ให้กลายเป็นค่าลบขนาดใหญ่ ซึ่งเป็นหายนะ DSP engine สามารถให้ค่าอิ่มตัว (saturate) แทนได้ คือผลลัพธ์จะค้างอยู่ที่ +0.99997 ซึ่งเป็นค่าที่ใกล้ที่สุดที่เก็บได้

DSP engine ของ dsPIC33CK:

X bus (W8) --+ +-------- accumulator A: 40 bits -------+ +--> 17x17 multiplier --->| 8 guard bits | 32 bits (Q31 fraction) |--> SAC.R: round, Y bus (W10) --+ (fractional: << 1) +---------------------------------------+ saturate, store accumulator B: the same MAC w4*w6, A, [w8]+=2, w4, [w10]+=2, w6 = A += w4*w6 AND fetch the next two operands, in ONE cycle
  • แอคคิวมูเลเตอร์ขนาด 40 บิต 2 ตัว คือ A และ B ประกอบด้วย 32 บิตบวกกับบิตกันล้น (guard bits) 8 บิต ผลรวมระหว่างทางสามารถเกิน ±1 ได้สูงสุดถึง 256× โดยไม่สูญหาย ตราบใดที่ผลลัพธ์สุดท้ายยังเก็บได้พอดี
  • MAC (การคูณสะสม, multiply-accumulate) ทำ A += x × y ได้ใน 1 รอบคำสั่ง และในรอบเดียวกันนั้นยังโหลดค่า x ตัวถัดไปผ่าน W8 และค่า y ตัวถัดไปผ่าน W10 ด้วย เมื่ออยู่ในลูป REPEAT จะได้แท็ปของฟิลเตอร์ (tap) หนึ่งแท็ปต่อหนึ่งรอบคำสั่ง
  • CORCON ใช้กำหนดโหมด: SATA/SATB ให้แอคคิวมูเลเตอร์อิ่มตัว, SATDW ให้ค่าอิ่มตัวเมื่อเก็บค่า, RND เลือกวิธีปัดเศษ, IF เลือกการคูณแบบจำนวนเต็มหรือแบบเศษส่วน

สองเรื่องที่พบระหว่างเขียนการทดลองนี้: คอมไพเลอร์ต้องการให้ประกาศแอคคิวมูเลเตอร์เป็น volatile register int acc asm("A") (หากไม่มี volatile คอมไพเลอร์อาจหยุดพร้อมข้อความ “Expected DSP accumulator result”) และ __builtin_mac ที่อยู่ในลูป for ของภาษา C ธรรมดาไม่ได้เร็วกว่า C ธรรมดาเลย เพราะการโหลดข้อมูลและตัวนับรอบลูปใช้ประมาณ 10 รอบคำสั่ง การจะได้ความเร็วเต็มที่ต้องใช้ REPEAT + MAC พร้อม prefetch ซึ่งเขียนเป็นแอสเซมบลีแบบ inline เพียงไม่กี่บรรทัด (dspDotFast()) ตัวถูกดำเนินการตัวที่สองต้องอยู่ใน Y memory (0x3000–0x4FFF บนชิปนี้) บัฟเฟอร์เหล่านั้นจึงถูกประกาศเป็น DSP_YMEM

ฟิลเตอร์ FIR ฟิลเตอร์แบบ Finite Impulse Response คำนวณเอาต์พุตแต่ละค่าเป็นผลรวมถ่วงน้ำหนักของอินพุต N ค่าล่าสุด: y[n] = h[0]x[n] + h[1]x[n−1] + … + h[N−1]x[n−N+1] ซึ่งก็คือผลคูณจุด (dot product) ใช้ MAC N ครั้งต่อหนึ่งแซมเปิล ค่าน้ำหนัก h เป็นตัวกำหนดว่าฟิลเตอร์ทำอะไร สเก็ตช์จะออกแบบฟิลเตอร์ผ่านต่ำด้วยวิธี windowed-sinc (ทำครั้งเดียวด้วย float) แล้วแปลงค่าน้ำหนักเป็น Q15

Goertzel หากต้องการทราบว่าความถี่หนึ่งความถี่ในบล็อกของแซมเปิลมีความแรงเท่าใด ไม่จำเป็นต้องใช้ FFT ทั้งหมด อัลกอริทึม Goertzel เป็นฟิลเตอร์แบบเวียนเกิด (recursive) ขนาดเล็กที่ปรับให้ตรงกับความถี่นั้น โทรศัพท์ใช้อัลกอริทึมนี้ในการจดจำเสียง DTMF ทั้ง 8 เสียงของแป้นกด (แต่ละปุ่ม = เสียงของแถว 1 เสียง + เสียงของคอลัมน์ 1 เสียง)

1. การคูณ Q15 ด้วยฟังก์ชัน builtin สำหรับการคูณ 16×16→32 ของคอมไพเลอร์:

inline q15 q15mul(q15 a, q15 b) { return (q15)(__builtin_mulss(a, b) >> 15); }

2. ผลคูณจุด (dot product) ด้วย MAC builtin (ใช้กับหน่วยความจำส่วนใดก็ได้ ประมาณ 10 รอบคำสั่งต่อสมาชิก):

volatile register int acc asm("A");
acc = __builtin_clr();                                         /* A = 0 */
for (uint16_t i = 0; i < n; i++)
    acc = __builtin_mac(acc, x[i], y[i], 0, 0, 0, 0, 0, 0, 0, 0);   /* A += x*y */
return __builtin_sacr(acc, 0);                                 /* round, saturate, store */

3. แบบที่เร็ว: REPEAT + MAC พร้อม prefetch (dspDotFast()) CLR ดึงข้อมูลคู่แรก MAC แต่ละครั้งจะคูณคู่ที่ดึงมาก่อนหน้าและดึงคู่ถัดไป REPEAT สั่งให้คำสั่งถัดไปทำงานซ้ำ n−1 ครั้งโดยไม่มีงานส่วนเกินของลูป:

"mov    %1, w8"                               /* x pointer, X bus */
"mov    %2, w10"                              /* y pointer, Y bus: must be in Y memory */
"sub    %3, #2, w0"
"clr    A, [w8]+=2, w4, [w10]+=2, w6"         /* A = 0, fetch x0, y0 */
"repeat w0"                                   /* next line n-1 times */
"mac    w4*w6, A, [w8]+=2, w4, [w10]+=2, w6"  /* A += x*y, fetch next */
"mac    w4*w6, A"                             /* last pair */
"sac.r  A, %0"                                /* round, saturate, store */

4. เทคนิคของบัฟเฟอร์หน่วงสัญญาณ (delay line) ของ FIR (firRun()) อินพุตแต่ละค่าจะถูกเขียนสองครั้ง ที่ตำแหน่ง pos และ pos + n ลงในบัฟเฟอร์ขนาด 2N แซมเปิล ทำให้อินพุต N ค่าล่าสุดเรียงต่อกันเป็นบล็อกเดียวที่เริ่มจาก pos เสมอ และการหาผลคูณจุดกับสัมประสิทธิ์เพียงครั้งเดียวก็ได้เอาต์พุต โดยไม่ต้องตรวจสอบการวนค่ากลับเลย:

f.pos = (f.pos == 0) ? f.n - 1 : f.pos - 1;     /* newest sample goes "in front" */
f.x[f.pos] = in;
f.x[f.pos + f.n] = in;
return dspDotFast(f.h, &f.x[f.pos], f.n);       /* h[k] * x[n-k] */

5. RMS ผลรวมกำลังสองของ 256 แซมเปิลมีค่ามากกว่า 1.0 มาก บิตกันล้นจะเก็บค่านี้ไว้ได้ (เมื่อปิด SATA ซึ่งเป็นค่าเริ่มต้น) และ __builtin_sacd(acc, 7) จะเก็บค่าโดยเลื่อนไปทางขวา 7 บิตเพื่อให้พอดีกับ 32 บิต

อธิบายการทำงานของโค้ด

1. สัญญาณนาฬิกาและโหมด (pwm6Begin() และ pwm6Frequency() ใน PWM6.h):

_PWMMD = 0;                                 /* power the PWM module */
PCLKCON = 0x0001;                           /* MCLKSEL = 01: FVCO / 2 */
*g.CONH   = (i == 0) ? 0x0000 : 0x0001;     /* PG2, PG3 start with PG1 (SOCS = 1) */
*g.IOCONH = IOCONH_PMOD_IND | IOCONH_PENH | IOCONH_PENL;   /* independent, PWM owns both pins */
*g.CONL   = CONL_CLK_MCLK | CONL_IND_DUAL;  /* master clock, MODSEL = 010 */
*g.PER    = ticks - 1;                      /* period = PER + 1 ticks */

เมื่อต่ำกว่า 6.1 kHz ค่าคาบจะเกินขนาด 16 บิต ดังนั้น CLKSEL = 10 จึงเลือกใช้ตัวหารสัญญาณนาฬิกา และ PCLKCON.DIVSEL กำหนดอัตราหาร 1:2 … 1:16 ตัวสร้างสัญญาณถูกเปิดตามลำดับ PG3, PG2, PG1 เพื่อให้ตัวที่ทำงานตามทั้งสองตัวรอคาบแรกของ PG1 อยู่แล้ว

2. การเขียนค่าหนึ่งช่อง (pwm6Write()) จุดเริ่มต้นและความกว้างในหน่วยติ๊กจะถูกแปลงเป็นรีจิสเตอร์ขอบสัญญาณสองตัว ขอบขาลงที่เลยจุดสิ้นสุดของคาบจะวนค่ากลับ (wrap-around) ส่วน 0 % และ 100 % ใช้การบังคับเอาต์พุต (override):

if (w == 0 || !pwm6Running) io = (io | ovrEn) & ~ovrHi;     /* hold low */
else if (w >= T)            io = io | ovrEn | ovrHi;        /* hold high */
else {
    uint16_t e = (s + w) % T;                               /* falling edge */
    if (L) { *g.TRIGA = s; *g.TRIGB = e; }
    else   { *g.PHASE = s; *g.DC = e; }
    io &= ~ovrEn;
}
*g.STAT |= STAT_UPDREQ;     /* load the new edges at the next period start */

UPDREQ ทำให้การเปลี่ยนค่าไม่เกิดสัญญาณผิดเพี้ยน (glitch): ฮาร์ดแวร์จะคัดลอกค่าใหม่ตอนเริ่มคาบถัดไป และจะไม่เปลี่ยนกลางพัลส์

3. การดิทเทอร์ (_PWM1Interrupt ซึ่งเปิดใช้เฉพาะขณะที่มีช่องที่กำลังดิทเทอร์อยู่):

pwm6DitherAcc += pwm6DitherFrac;            /* 0..15 sixteenths per period */
uint16_t w = pwm6DitherBase;
if (pwm6DitherAcc >= 16) { pwm6DitherAcc -= 16; w++; }

ทดสอบความเข้าใจ

PWM ความถี่ 100 kHz ที่ใช้สัญญาณนาฬิกา 400 MHz มีความละเอียดกี่บิต?

400 MHz / 100 kHz = 4000 ติ๊กต่อคาบ; log2(4000) = 12.0 บิต

ตัวสร้างสัญญาณสามตัวสร้างเอาต์พุตอิสระหกช่องได้อย่างไร?

ในโหมด independent edge, dual output ตัวสร้างสัญญาณแต่ละตัวมีรีจิสเตอร์ขอบสัญญาณสองคู่ คือ PHASE/DC สำหรับขา H และ TRIGA/TRIGB สำหรับขา L ทั้งหกช่องใช้คาบของตัวสร้างสัญญาณของตนร่วมกัน

การดิทเทอร์ให้อะไร และต้องแลกกับอะไร?

ให้ดิวตี้ไซเคิลเฉลี่ยที่ละเอียดกว่าหนึ่งติ๊ก (ในที่นี้คือ 1/16 ติ๊ก) สิ่งที่ต้องแลกคือริปเปิลเล็กน้อยที่ความถี่ PWM หารด้วย 16 ซึ่งโหลดหรือฟิลเตอร์ต้องกรองให้เรียบ และภาระของอินเทอร์รัปต์เล็กน้อย

เหตุใดสเก็ตช์จึงวัดความถี่ PWM ของตัวเอง?

สัญญาณนาฬิกา PWM มาจาก VCO ของ PLL ซึ่งค่าที่แน่นอนบนบอร์ดนี้ยังไม่ได้รับการยืนยัน การวัดด้วย SCCP2 (ซึ่งใช้สัญญาณนาฬิกาจาก FCY) จะแสดงค่าสัญญาณนาฬิกาจริง และค่าในหน่วย ns ทุกค่าจะถูกแก้ตามค่านั้น

สถานะ: คอมไพล์ผ่านที่ 100 MIPS (ทั้งแบบมีและไม่มี bootloader) โดยไม่มีคำเตือน ที่ 4 MIPS จะหยุดด้วย #error ตามที่ตั้งใจไว้ ใน MPLAB simulator รีจิสเตอร์ทุกตัวถูกเขียนค่าตามที่ตั้งใจไว้ (คาบ เฟส ดิวตี้ไซเคิล TRIGA/TRIGB ของทั้งหกช่อง ตัวหารสัญญาณนาฬิกา การบังคับเอาต์พุตสำหรับ 0 / 100 % และการหยุด และอินเทอร์รัปต์สำหรับการดิทเทอร์) แต่ตัวจำลองไม่มีแบบจำลองของ PWM จึงไม่มีสัญญาณใดออกมาที่ขา ยังไม่ได้ทดสอบกับฮาร์ดแวร์จริง

  • หลังการทดลองนี้ ผู้เรียนสามารถอ่านทุกช่องสัญญาณที่ความละเอียดเต็ม 12 บิตด้วยฟังก์ชันของ ADC.h ได้ ทั้งทีละช่องและทุกช่องพร้อมกันจากทริกเกอร์เดียว
  • หลังการทดลองนี้ ผู้เรียนสามารถเลือกความละเอียดและเวลาสุ่มตัวอย่าง (sample time) และอธิบายได้ว่าทั้งสองค่าส่งผลต่อความแม่นยำและความเร็วอย่างไร
  • หลังการทดลองนี้ ผู้เรียนสามารถสุ่มตัวอย่างด้วยอัตราที่แม่นยำโดยใช้ทริกเกอร์ฮาร์ดแวร์ (ไทเมอร์หรือ PWM) และเก็บผลลัพธ์ในอินเทอร์รัปต์ได้
  • หลังการทดลองนี้ ผู้เรียนสามารถใช้วงจรเปรียบเทียบดิจิทัลและฟิลเตอร์การสุ่มเกิน / การหาค่าเฉลี่ย และวัด AVDD ด้วยแรงดันอ้างอิง band gap ได้

ความรู้พื้นฐาน

สิ่งที่ analogRead() ซ่อนไว้ analogRead(A0) เริ่มการแปลงสัญญาณ (conversion) หนึ่งครั้ง รอจนเสร็จ แล้วคืนค่า 10 บิต (0–1023) เหมือน Arduino แบบดั้งเดิม แต่ฮาร์ดแวร์ให้ค่าได้ 12 บิต (0–4095) และทำได้มากกว่านั้นอีกมากโดยไม่ใช้ CPU ได้แก่ เริ่มการแปลงสัญญาณจากไทเมอร์หรือ PWM แปลงหลายช่องสัญญาณจากทริกเกอร์เดียว เปรียบเทียบผลลัพธ์กับค่าขีดจำกัด และรวมผลลัพธ์หลายค่าเพื่อเพิ่มความละเอียด

โครงสร้างของ ADC ชิป MC005 มีแกนแบบการประมาณค่าแบบต่อเนื่อง (successive approximation, SAR) ขนาด 12 บิตหนึ่งแกน (เรียกว่า “แกนร่วม (shared core)”; ชิปรุ่น MP ที่ใหญ่กว่ามีแกนเฉพาะ (dedicated core) เพิ่มด้วย) ต่ออยู่หลังมัลติเพล็กเซอร์ที่มีอินพุต 22 ช่อง จุดที่ทำให้ ADC นี้มีความสามารถสูงคือ การตั้งค่าส่วนใหญ่มีแยกสำหรับแต่ละช่องสัญญาณ:

ทริกเกอร์ การแปลงสัญญาณจะเริ่มเมื่อแหล่งทริกเกอร์ของช่องสัญญาณนั้นทำงาน แหล่งทริกเกอร์ได้แก่ การสั่งเริ่มด้วยซอฟต์แวร์เฉพาะช่อง (ซึ่ง adcRead() และ analogRead() ใช้) ทริกเกอร์ซอฟต์แวร์ร่วม (common software trigger) (การเขียนครั้งเดียวเริ่มทุกช่องที่ตั้งไว้ให้ใช้ทริกเกอร์นี้) ทริกเกอร์ซอฟต์แวร์แบบระดับ (level software trigger) (แปลงสัญญาณซ้ำไปเรื่อย ๆ ตราบที่ยังเปิดอยู่) เหตุการณ์จาก PWM generator ไทเมอร์ SCCP เอาต์พุตของ CLC และ PTG (Lab 33) ทริกเกอร์ฮาร์ดแวร์ให้ตัวอย่างที่มีช่วงห่างเท่ากันพอดี ซึ่งลูปที่ใช้ delay() ไม่มีทางทำได้

ความละเอียดและความเร็ว ที่ 12 บิตและแรงดันอ้างอิง 3.3 V หนึ่งขั้น (LSB) มีค่า 0.8 mV ความละเอียด 10, 8 และ 6 บิตหยาบกว่าแต่แปลงสัญญาณได้เร็วกว่า เวลาสุ่มตัวอย่าง (sample time) คือระยะเวลาที่อินพุตใช้ชาร์จตัวเก็บประจุสุ่มตัวอย่าง (sample capacitor) ของ ADC ก่อนเริ่มการแปลงสัญญาณ แหล่งสัญญาณที่มีความต้านทานสูง (เช่น pot 10 kΩ) ต้องใช้เวลานี้มากขึ้น

การสุ่มเกิน (oversampling) การรวมผลลัพธ์ 4 ค่าแล้วหารผลรวมด้วยสองจะได้บิตเพิ่มหนึ่งบิต ถ้าสัญญาณมีสัญญาณรบกวน (noise) อยู่เล็กน้อย: 4× → 13 บิต, 16× → 14 บิต, 64× → 15 บิต, 256× → 16 บิต ฟิลเตอร์ฮาร์ดแวร์ทำสิ่งนี้ได้เอง ในโหมดการหาค่าเฉลี่ย (averaging) ฟิลเตอร์จะคืนค่าเฉลี่ยของผลลัพธ์ N ค่า ซึ่งช่วยลดสัญญาณรบกวนและคงความละเอียดไว้ที่ 12 บิต

รูปแบบข้อมูล ผลลัพธ์แบบจำนวนเต็ม (integer)จัดชิดขวา (0–4095) ผลลัพธ์แบบเศษส่วน (fractional)จัดชิดซ้ายใน 16 บิต ซึ่งเหมาะกับการคำนวณแบบ Q15 (Lab 36) แบบมีเครื่องหมาย (signed)ให้ค่าแบบ two’s complement รอบจุดกึ่งกลางสเกล และแบบผลต่าง (differential)วัดค่าของช่องสัญญาณลบด้วยอินพุตขั้วลบ ANN0

แรงดันอ้างอิง band gap AN21 เป็นแรงดันอ้างอิงคงที่ประมาณ 1.2 V ภายในชิป ADC วัดค่านี้เทียบกับ AVDD ดังนั้น AVDD = 1.2 V × 4096 / ผลลัพธ์ สเก็ตช์ใช้ค่านี้แก้ค่ามิลลิโวลต์ทั้งหมด โดยไม่ต้องใช้โวลต์มิเตอร์

  2. ช่องสัญญาณเดียว: ส่ง r0 จะได้การแปลงสัญญาณ AN0 จำนวน 16 ครั้ง พร้อมค่าเฉลี่ย ค่าต่ำสุด ค่าสูงสุด และสัญญาณรบกวน (ส่วนเบี่ยงเบนมาตรฐานในหน่วย LSB) ลอง r17 สำหรับขาอื่น และ r21 สำหรับ band gap

  4. ความเร็วและเวลาสุ่มตัวอย่าง: ส่ง s จากนั้น s2 (เวลาสุ่มตัวอย่างสั้นที่สุด) และ s200 เมื่อหมุน pot ไว้ตรงกลาง (ความต้านทานของแหล่งสัญญาณ 5 kΩ) เวลาสุ่มตัวอย่างที่สั้นมากอาจอ่านค่าผิดไปเล็กน้อย ให้เปรียบเทียบกับ r0 หลังแต่ละคำสั่ง กลับค่าเดิมด้วย s17
  5. ทริกเกอร์จากไทเมอร์: ส่ง t1000 SCCP3 จะทริกเกอร์ AN0 1000 ครั้งต่อวินาทีเป็นเวลาหนึ่งวินาที และอินเทอร์รัปต์จะเก็บผลลัพธ์แต่ละค่า: ได้ประมาณ 1000 ตัวอย่าง ในครั้งแรก สเก็ตช์จะหาว่ารหัสทริกเกอร์ใดใช้ได้กับชิปของผู้เรียนแล้วพิมพ์ออกมา ลอง t50000

  7. แบบต่อเนื่อง: ส่ง l ทริกเกอร์แบบระดับ (level trigger) จะแปลงสัญญาณ AN0 ต่อเนื่องติดกันเป็นเวลา 100 ms: เป็นอัตราสูงสุดที่ ADC ทำได้

อธิบายการทำงานของโค้ด

1. การตั้งค่าเริ่มต้น (adcBegin() ใน ADC.h) จ่ายไฟให้โมดูล เลือก 12 บิตและรูปแบบจำนวนเต็ม เลือกสัญญาณนาฬิกา (FOSC / 4 = 50 MHz ที่ 100 MIPS, TAD = 40 ns ต่ำกว่าขีดจำกัด 70 MHz) และเวลาสุ่มตัวอย่าง จากนั้นเปิด ADC และจ่ายไฟให้แกนร่วม:

_ADC1MD = 0;
ADCON1Hbits.SHRRES = 3;                 /* 12 bit */
ADCON2Lbits.SHRADCS = 1;                /* TAD = 2 ADC clocks */
ADCON2Hbits.SHRSAMC = 15;               /* sample time 17 TAD */
ADCON3Hbits.CLKSEL = 1;                 /* ADC clock source = FOSC */
ADCON3Hbits.CLKDIV = 3;                 /* 200 MHz / 4 = 50 MHz */
ADCON3Hbits.SHREN = 1;                  /* shared core on */
ADCON1Lbits.ADON = 1;
ADCON5Lbits.SHRPWR = 1;                 /* power the shared core ... */
while (!ADCON5Lbits.SHRRDY) { }         /* ... and wait until it is ready */

2. รีจิสเตอร์ของแต่ละช่องสัญญาณผ่านดัชนี แหล่งทริกเกอร์มีช่องละหนึ่งไบต์ และผลลัพธ์มีช่องละหนึ่งเวิร์ด ทั้งสองเรียงต่อกันโดยไม่มีช่องว่าง ดังนั้นพอยน์เตอร์ตัวเดียวจึงจัดการได้ทั้ง 22 ช่องสัญญาณ (ตรวจสอบกับ linker script แล้ว):

static volatile uint16_t *const adcBuf = &ADCBUF0;          /* ADCBUF0..21, one per channel */
inline volatile uint8_t *adcTrgReg(uint8_t ch) { return (volatile uint8_t *)&ADTRIG0L + ch; }

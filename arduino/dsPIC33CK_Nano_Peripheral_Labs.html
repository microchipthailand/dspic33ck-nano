Setup

These labs use the same board, board package and tools as Labs 01–30. If you have done Lab 01, you are ready.

  1. Install the tools and the board package as described in the main guide, Setup (XC-DSC v4.00 or newer, MPLAB X for ipecmd, Arduino IDE 2.x, Boards Manager URL).
  2. Tools → Board → dsPIC33CK Nano (dsPIC33CK256MC005). Tools → Clock → 100 MIPS. Labs 31 and 37 need it (their peripherals are clocked from the PLL); the others also run at 4 MIPS.
  3. The examples are in their own folder: File → Examples → dsPIC33CK_Nano_Peripherals → Lab31_AnalogComparator … Lab38_AdvancedADC.
  4. Every lab talks to you over Serial: a 3.3 V USB-serial adapter on J5 (J5-2 TX → adapter RX, J5-3 RX ← adapter TX, J5-4 GND), Serial Monitor at 115200 baud. Set the line ending to Newline: most labs take commands with numbers, such as v1200 or d1 25.5.
  5. Lab 35 must be uploaded with the PICkit on J4 (Tools → Bootloader → None), because it sets configuration words. All other labs also work with the serial bootloader.
How each lab is built: the sketch (.ino) stays short and readable. The driver code for the peripheral is in a second tab (Comparator.h, PPS.h, PTG.h, CRC.h, DMT.h, DSP.h, PWM6.h, ADC.h). Each tab starts with a summary of the peripheral and its registers, so you can copy it into your own project.
3.3 V only. All pins are 3.3 V. In Lab 37 the PWM pins only drive LEDs or a logic analyser: never connect them to a power stage (MOSFETs, motor driver) without a proper gate driver.

The dsPIC33CK256MC005 and its peripherals

What is inside the chip, and why these eight labs are worth doing.

The dsPIC33CK256MC005 is a Digital Signal Controller: a 16-bit microcontroller with a DSP engine, running at up to 100 MIPS. The “MC” stands for Motor Control, the “005” for the 48-pin package with 256 KB flash and 16 KB RAM. Labs 01–30 used the peripherals every microcontroller has (GPIO, UART, SPI, I2C, ADC, timers) and a few bigger ones (DMA, CAN FD, motor PWM). Labs 31–37 cover the ones that make this family different. Most of them work without the CPU: once you set them up, they run by themselves.

31Analog comparator: a fast “above or below” detector

Compare a voltage with a threshold from the internal 12-bit DAC, tame noise with hysteresis, send the result straight to a pin, count edges, and build an ADC out of the DAC and the comparator.

peripheralCMP1DAC1hysteresisdigital filterPPS outputedge interruptSAR ADC

Objectives

  • After this lab you can set up comparator CMP1 with its DAC as the threshold, and choose one of its four inputs.
  • After this lab you can explain hysteresis and measure how it stops an output from chattering.
  • After this lab you can send the comparator output to any remappable pin with PPS, with no CPU in the path.
  • After this lab you can count comparator edges in an interrupt and use that as a frequency counter.
  • After this lab you can explain how a successive-approximation (SAR) ADC works, because you built one from the DAC and the comparator.

Background

What a comparator is. A comparator has two inputs and a one-bit output. The output is 1 when the + input is higher than the − input, and 0 otherwise. It is an ADC with exactly one bit, but it answers continuously and very fast: the dsPIC33CK comparator reacts in about 15 ns. The ADC needs about a microsecond per sample, and the CPU has to look at every result. The comparator only reports when something changes.

Where it is used. Over-current protection in motor drives and power supplies (the comparator can switch a PWM off in nanoseconds, long before software would notice), zero-crossing detection on AC signals, a battery-low alarm that costs no CPU time, and reading signals that are not clean logic levels.

On the dsPIC33CK. The comparator and its DAC form one module, called DAC1 in the register names. The DAC drives the − input, so the threshold is set by software with 0.8 mV steps. The + input is one of four pins, selected by INSEL:

Hysteresis. A slowly moving signal with a little noise on it crosses the threshold many times on its way through, and the output chatters: ten edges for one real crossing. Hysteresis moves the threshold a little once the output has switched, so the signal has to come back by that amount before the output switches back. Noise smaller than the hysteresis is then ignored. The dsPIC33CK offers 0, 15, 30 or 45 mV (HYSSEL).

input ~~~~~/\/\/\/~~~~~~~~ without hysteresis: output _____|‾|_|‾|_|‾‾‾‾‾‾ (chatter) threshold --------------------- with 30 mV: output _____|‾‾‾‾‾‾‾‾‾‾‾‾‾ (one clean edge)

The digital filter (FLTREN) is a second cure: it ignores pulses shorter than a few clock cycles.

The clock. The DAC is clocked from the PLL (DACCTRL1L.CLKSEL = FPLLO). That is why this lab needs Tools → Clock = 100 MIPS; at 4 MIPS the PLL is off and the sketch stops with an #error.

A SAR ADC out of the comparator. Most ADCs inside microcontrollers, including this one’s, are successive-approximation ADCs. They find the input voltage the way you would guess a number between 0 and 4095 by asking “higher or lower?”: try 2048, then 1024 or 3072, and so on, 12 questions for 12 bits. With the DAC as the guess and the comparator as the answer, the sketch does exactly that.

bit 11: DAC = 2048 (1650 mV) input above? yes -> keep bit 11 code = 2048 bit 10: DAC = 3072 (2475 mV) input above? no -> drop it code = 2048 bit 9: DAC = 2560 (2062 mV) input above? yes -> keep code = 2560 ... 12 steps ... code = input in 1/4096 of 3.3 V

Step by step

  1. Wire the pot (wiper on J2-15). Open Lab31_AnalogComparator, check Clock = 100 MIPS, upload, and open the Serial Monitor (115200, Newline). The status line shows input A, threshold 1650 mV, hysteresis 30 mV.
  2. Threshold: turn the pot slowly. Each time the wiper passes 1.65 V the Monitor prints # input ABOVE threshold or # input below threshold, and the USER LED follows: lit = above.
  3. Send v1000. The threshold is now 1.0 V: the switching point on the pot moves. Try v2500. Send v1650 to go back.
  4. Hysteresis: send h0 (none), then c. During the 5 s count, turn the pot very slowly once through the threshold. Note the number of edges. Repeat with h3 (45 mV). With no hysteresis you usually see several edges for one crossing; with 45 mV you see one. Try f (digital filter on) as well.
  5. Hardware output: send o. The USER LED is now driven directly by the comparator through PPS, with no software in between. It is active low, so it now lights when the output is low (below). Send p to invert the comparator, and it lights above the threshold again. With a scope on D9 you can see the same signal there, always.
  6. Frequency counter: fit the jumper J3-16 → J3-17. Send g (1 kHz tone on D8), d (input D), v1650 and n. The sketch counts the rising edges for one second and prints about 1000 Hz.
  7. SAR ADC: send a (back to input A, the pot) and then m. The sketch measures the pot voltage twice: with the DAC + comparator search (12 steps) and with analogRead(). Both values should agree within a few mV.
  8. Plotter: send s, close the Monitor, open Tools → Serial Plotter. You see the input, the threshold line, and the comparator output jumping between 0 and 3000.

How the code works

1. Setting up the module (cmpBegin() in Comparator.h). Power the module, give the DAC its PLL clock, choose the input, set the threshold, enable the interrupt for both edges, then switch on this DAC (DACEN) and the DAC block (DACON):

_CMP1MD = 0;                        /* power the module (PMD7) */
DACCTRL1Lbits.CLKSEL = 3;           /* FPLLO */
cmpSelectInput(input);              /* INSEL + make the pin analog */
cmpThresholdCodeSet(cmpThresholdCode);
DAC1CONLbits.IRQM = 3;              /* interrupt on both edges */
DAC1CONLbits.DACEN = 1;
DACCTRL1Lbits.DACON = 1;
_CMP1IP = 3; _CMP1IF = 0; _CMP1IE = 1;

2. The threshold in millivolts. DAC1DATH = mV × 4096 / 3300, rounded.

3. Counting edges. The interrupt runs on every change of the output, so it counts all edges, and separately the rising ones (the output is already 1 when the interrupt runs after a rising edge):

extern "C" void __attribute__((interrupt, no_auto_psv)) _CMP1Interrupt(void)
{
    cmpEdges++;
    if (DAC1CONLbits.CMPSTAT) cmpRises++;
    _CMP1IF = 0;
}

4. Output on a pin. PPS output code 23 is “CMP1”. Writing it into the RPnR byte of a pin connects the comparator to that pin (see Lab 32 for how PPS works):

rpor[rp - 32] = on ? 23 : 0;        /* RPOR byte of pin RPn: 23 = CMP1, 0 = normal port pin */

5. The SAR search (cmpMeasureCode()). Hysteresis, inversion and the interrupt are switched off for the search, so they cannot disturb it. Each step waits 2 µs for the DAC to settle:

for (int8_t bit = 11; bit >= 0; bit--) {
    uint16_t trial = code | (1U << bit);
    DAC1DATH = trial;
    delayMicroseconds(2);                       /* DAC + comparator settle */
    if (DAC1CONLbits.CMPSTAT) code = trial;     /* input still above: keep the bit */
}

Check your understanding

Why can a comparator react faster than software that reads the ADC?

It is a continuous analog circuit: its output changes about 15 ns after the input crosses the threshold, and it can trigger an interrupt or drive a pin directly. Software has to start a conversion, wait for it, read it and compare, which takes microseconds, and it only sees the signal when it looks.

What does 45 mV of hysteresis mean for a signal that rises slowly through 1.65 V?

The output switches to 1 near 1.65 V. To switch back to 0 the signal must fall about 45 mV lower. Noise smaller than that cannot switch the output back and forth.

How many comparator decisions does a 12-bit SAR conversion need, and why?

Twelve: each one decides one bit, from the most significant to the least, halving the remaining range every time.

Why does the LED light “the wrong way round” after the o command?

The USER LED is active low: it lights when its pin is low. With o the comparator output drives the pin directly, so the LED lights when the output is 0, below the threshold. Inverting the comparator with p fixes it.

32PPS: Peripheral Pin Select

Connect peripherals to the pins you choose while the program runs: move a PWM from pin to pin, feed one interrupt from different pins, wire peripherals together inside the chip with virtual pins, and lock the mapping.

Objectives

  • After this lab you can connect a peripheral output to a pin by writing its function code into the pin’s RPnR byte.
  • After this lab you can connect a peripheral input to a pin by writing the pin’s RP number into the input’s RPINR field.
  • After this lab you can use the virtual pins RPV0–RPV5 to connect two peripherals inside the chip, with no wire.
  • After this lab you can lock and unlock the mapping (IOLOCK) and explain why the lock exists.
  • After this lab you can read out the whole pin map of a running program.

Background

The problem PPS solves. On most small microcontrollers each peripheral is wired to fixed pins: UART1 TX is always pin X. A 48-pin chip with three UARTs, two SPIs, four timers and a CAN controller has more peripheral signals than pins, so the designer has to accept whatever combination the chip offers. On the dsPIC33CK most digital peripheral signals are not wired to pins at all. They go through a switchboard, the Peripheral Pin Select, and the program decides which pin carries what.

OUTPUTS: one byte per PIN INPUTS: one byte per PERIPHERAL INPUT RPOR13 low byte = RP58R (pin RC10) RPINR18 low byte = U1RXR writes "1" = U1TX -> UART1 TX drives RC10 writes "59" -> UART1 RX listens to RP59 (RC11) peripheral outputs pins U1TX(1) OCM1(15) CMP1(23) PTGTRG24(46) ... --->[ RPnR = code ]---> RP32..RP61, RP65, RP72, RP74, RP77 pins RPn --->[ INT1R / U2RXR / ICM2R ... = n ]---> peripheral inputs virtual pins RP176..RP181 (RPV0..5): an output written there can be read back by any input

Two directions, two rules. For an output the register belongs to the pin: the pin’s RPnR byte says which peripheral drives it. So one peripheral output can drive several pins at the same time. For an input the register belongs to the peripheral: INT1R, U1RXR and so on hold the RP number of the pin to listen to. So several peripherals can listen to the same pin.

RP numbers on this chip. RP32–RP47 are RB0–RB15, RP48–RP61 are RC0–RC13, plus RP65 (RD1), RP72 (RD8), RP74 (RD10), RP77 (RD13). RA0–RA4 have no RP number: they cannot be remapped. RP176–RP181 are the virtual pins RPV0–RPV5. They have no pad on the package; they exist only to connect a peripheral output to a peripheral input inside the chip.

What PPS does not do. It only connects the signal. The pin still needs its TRIS bit (0 for an output) and, on a pin with an analog function, ANSEL = 0. Analog signals (ADC, comparator inputs) and a few fast signals (the PWM1–PWM3 pins, I2C1) are not on PPS: they have fixed pins.

The lock. A program that accidentally writes into an RPOR register could move the UART or a motor PWM to another pin. So the mapping can be locked: RPCON.IOLOCK = 1 ignores every write to the PPS registers. Unlocking needs a key sequence, which the compiler builtin __builtin_write_RPCON(0x0000) performs; __builtin_write_RPCON(0x0800) locks again. On this chip the lock is not one-way: it can be unlocked again later. The core itself does exactly this in Serial.begin() and analogWrite().

How the code works

1. Finding a pin’s output byte (ppsOutReg() in PPS.h). The RPOR registers hold two pins each and follow each other without gaps from RP32 (RPOR0 low byte) to RP77; the virtual pins follow in RPOR24–26. So a byte pointer does the job (checked against the addresses in the linker script):

volatile uint8_t *ppsOutReg(uint8_t rp)
{
    volatile uint8_t *base = (volatile uint8_t *)&RPOR0;
    if (rp >= 32 && rp <= 77)   return base + (rp - 32);
    if (rp >= 176 && rp <= 181) return base + 48 + (rp - 176);
    return 0;
}

2. Writing a mapping with the lock. ppsOutput() remembers whether PPS was locked, unlocks, writes, and locks again if it was locked before. Inputs are named bit fields in the device header (_INT1R, _U2RXR), so ppsInput() is a macro around the same lock handling:

ppsOutput(61, PPS_OCM1);        /* SCCP1 output -> RC13 (RP61)            */
ppsOutput(61, PPS_NONE);        /* RC13 back to a plain port pin          */
ppsInput(_INT1R, 60);           /* INT1 input  <- RC12 (RP60)             */

3. The signal to move around. pwmBegin() sets up SCCP1 as a 1 kHz PWM (MOD = 0101, dual-edge buffered). loop() changes the duty on a squared sine, so the LED appears to breathe. The PWM itself never changes; only its pin does.

Background

Why a trigger generator. Many control tasks need things to happen in an exact order at exact times: “at the PWM midpoint, wait 300 ns, sample current A, then B, then 2 µs later the voltage, eight times per period”. Doing that in software means interrupts, and interrupts have jitter: they are delayed whenever another interrupt runs or interrupts are off. The Peripheral Trigger Generator is a tiny processor that does nothing but this. It has its own program of up to 32 one-byte steps, two 16-bit timers, two loop counters and a step-delay timer, and it fires triggers into other peripherals. It runs on its own clock and never waits for the CPU.

+---------------- PTG ----------------+ inputs ----> | step queue PTGQUE0..15 (32 steps) | ----> trigger outputs 0..31 (ADC trigger = 12, PWM1-4 (0-3) | PTGQPTR = step now running | PPS pins = 24, 25, PPS inputs RP6/RP7 = 26, 27) SCCP4 (7) | Timer0 / Timer1 (PTGT0LIM/T1LIM) | ----> interrupts PTG0..PTG3 to the CPU CMP1 (9) | counter 0 / 1 (PTGC0LIM/C1LIM) | ADC (13) | step delay (PTGSDLIM) | INT2 pin (15) | clock = FCY / PTGDIV | +--------------------------------------+

A step is one byte: the command in the high four bits, an option in the low four. The sketch has a macro for each one (in PTG.h):

Timing. The PTG clock is FCY divided by PTGDIV (1–32). The sketch uses ÷32: 3.125 MHz at 100 MIPS, 125 kHz at 4 MIPS. Timer0 is 16-bit, so one wait is at most 65536 clocks (21 ms at 100 MIPS). Longer delays are a wait inside a counter loop. The sketch computes PTGT0LIM from microseconds, so the programs have the same timing at both clock settings.

Outputs to pins. Trigger outputs 24 and 25 are on PPS (output codes 46 and 47), so they can drive any remappable pin. With PTGCST.PTGTOGL = 1 each PTG_TRIG step toggles its output; with 0 it makes a short pulse. Toggling makes square waves you can see on an LED.

Why does the LED rhythm not change during the busy test, while the Serial print-out stops?

It jumps back to step 0 24 times (adding 1 to counter 0 each time), then clears the counter and continues, so the loop body runs 25 times.

Background

What a CRC is. A Cyclic Redundancy Check treats the message as one long binary number and divides it by a fixed number, the generator polynomial, using XOR instead of subtraction. The remainder is the CRC. The sender appends it; the receiver computes it again and compares. One bit wrong anywhere changes the remainder.

Why not just add the bytes? A sum does not notice swapped bytes, and two errors can cancel each other. A good CRC detects every single-bit and two-bit error, every odd number of bit errors, and every burst of errors shorter than the CRC itself. That is why Ethernet, USB, CAN, Modbus, ZIP files and the serial bootloader of this board all use CRCs.

In hardware it is a shift register. The division can be done one bit at a time with a shift register and a few XOR gates where the polynomial has 1 bits:

CRC-16/CCITT, polynomial x^16 + x^12 + x^5 + 1 = 0x1021 data bit in -->(XOR)-->[ register bit 0 ... 4 ]--(XOR)-->[ bit 5 ... 11 ]--(XOR)-->[ bit 12 ... 15 ]--+ ^ ^ ^ | +---------------------------------+--------------------------+-------------------+ feedback = bit 15

In software this costs about ten instructions per bit. The engine shifts one bit per instruction cycle while the CPU goes on writing the next bytes into its 16-byte FIFO.

The dsPIC33CK engine, and two things to know. You set the polynomial length (PLEN), the data width (DWIDTH, here 8 bits), the polynomial (CRCXOR), the start value (CRCWDAT) and the bit order (LENDIAN), start it with CRCGO and write bytes into CRCDATL. The engine used here (legacy mode) is the textbook “augmented” shift register, which differs from the usual CRC definition in two ways. Both were found in this lab’s testing, and crcHw() handles them:

  • At the end, width zero bits must be shifted through after the data: for CRC-16 two zero bytes, for CRC-32 four.
  • At the start, the usual “direct” init value must be converted into the matching “indirect” seed, by running the shift register backwards width steps. For CRC-16/CCITT, 0xFFFF becomes 0x84CF.

The register always shifts MSB first, so for a reflected CRC the data goes in LSB first (LENDIAN = 1) and the result is bit-reversed at the end.

How the code works

1. Describing a CRC. Each catalogue entry is a CrcSpec with the six parameters and the check value, so one function handles all of them:

const CrcSpec CRC16_MODBUS = { "CRC-16/MODBUS", 16, 0x8005, 0xFFFF, true, true, 0x0000, 0x4B37 };

2. Starting the engine (crcHwBegin() in CRC.h):

_CRCMD = 0;                            /* power the module */
CRCCONL = 0; CRCCONH = 0;              /* off: clears FIFO and state */
CRCCONLbits.CRCEN = 1;
CRCCONLbits.MOD = 0;                   /* legacy: augmented shift register */
CRCCONLbits.LENDIAN = s.refin;         /* reflected input = LSB first */
CRCCONHbits.PLEN = s.width - 1;
CRCCONHbits.DWIDTH = 8 - 1;            /* we feed bytes */
CRCXORL = s.poly & 0xFFFE; CRCXORH = s.poly >> 16;   /* bit 0 is implied */
seed = crcIndirectSeed(s.init, s.poly, s.width);
CRCWDATL = seed; CRCWDATH = seed >> 16;
_CRCIF = 0;
CRCCONLbits.CRCGO = 1;

3. Feeding bytes. With DWIDTH = 7 the FIFO takes byte writes and holds 16 of them. The loop only waits when the FIFO is full:

volatile uint8_t *fifo = (volatile uint8_t *)&CRCDATL;
while (CRCCONLbits.CRCFUL) { }
*fifo = data[i];

4. Finishing (crcHwEnd()): push width/8 zero bytes, wait until the FIFO is empty (CRCMPT) and the last bit has been shifted (CRCIF), read CRCWDAT, then reverse it for a reflected CRC and apply xorout.

5. The indirect seed runs the shift register backwards. When bit 0 of the register is 1, a feedback step must have happened, so the polynomial is XORed out and the top bit restored:

for (uint8_t i = 0; i < width; i++) {
    if (r & 1) r = ((r ^ poly) >> 1) | top;
    else       r >>= 1;
}

6. Reading flash. Program memory is 24 bits wide and is read with table-read instructions: TBLPAG = upper address bits, __builtin_tblrdl() the low 16 bits, __builtin_tblrdh() the upper 8.

Which errors does a 16-bit CRC always detect, and which can a simple sum miss?

A CRC-16 detects every single- and double-bit error, every odd number of bit errors (for polynomials with an x+1 factor) and every error burst up to 16 bits. A sum misses swapped bytes and two errors that cancel each other.

Why is “123456789” used to test CRC code?

Why does crcHwEnd() write zero bytes after the data?

In legacy mode the engine is an augmented shift register: the message has to be followed by width zero bits before the register holds the remainder.

Why is the engine fast even though it does one bit per cycle?

One bit per cycle is about 8 cycles per byte, and it runs in parallel with the CPU, which only writes bytes into the FIFO. Software needs about 10 instructions per bit, or 4 table look-ups per byte.

Background

Why not just use float? This chip has no floating-point unit. A float multiply is a library call of 30–100 instructions. Signal processing (filters, control loops, motor control) does millions of multiplications per second, so it uses fixed-point numbers instead: integers that are read as fractions.

Q15. An int16_t read as value / 32768. It covers −1 … +0.99997 in steps of 0.00003:

0x7FFF = +0.99997 0x4000 = +0.5 0x2000 = +0.25 0x0000 = 0 0xC000 = -0.5 0x8000 = -1.0 multiply: 0.5 x 0.5 = 0x4000 x 0x4000 = 0x10000000 (Q30) >> 15 = 0x2000 = 0.25

Two Q15 numbers multiplied give a Q30 result in 32 bits; shift it right by 15 to get Q15 back. +1.0 cannot be written in Q15, so −1 × −1 is a special case.

Overflow: wrap or saturate. 0.9 + 0.9 = 1.8 does not fit. Plain C integer arithmetic wraps around to a negative number (−0.2): in a filter or a control loop that turns a large positive value into a large negative one, a disaster. The DSP engine can saturate instead: the result sticks at +0.99997, the closest value it can hold.

The DSP engine of the dsPIC33CK:

X bus (W8) --+ +-------- accumulator A: 40 bits -------+ +--> 17x17 multiplier --->| 8 guard bits | 32 bits (Q31 fraction) |--> SAC.R: round, Y bus (W10) --+ (fractional: << 1) +---------------------------------------+ saturate, store accumulator B: the same MAC w4*w6, A, [w8]+=2, w4, [w10]+=2, w6 = A += w4*w6 AND fetch the next two operands, in ONE cycle
  • Two 40-bit accumulators A and B: 32 bits plus 8 guard bits. A running sum may exceed ±1 by up to 256× without being lost, as long as the final result fits.
  • MAC (multiply-accumulate) does A += x × y in one cycle, and in the same cycle loads the next x through W8 and the next y through W10. Inside a REPEAT loop that is one filter tap per cycle.
  • CORCON sets the mode: SATA/SATB saturate the accumulators, SATDW saturates when storing, RND chooses the rounding, IF integer or fractional multiply.

Two things found while writing this lab: the compiler needs the accumulator declared as volatile register int acc asm("A") (without volatile it may stop with “Expected DSP accumulator result”), and a __builtin_mac inside an ordinary C for loop is no faster than plain C, because the loads and the loop counter cost about 10 cycles. The full speed needs REPEAT + MAC with prefetch, written as a few lines of inline assembly (dspDotFast()). Its second operand must be in Y memory (0x3000–0x4FFF on this chip), so those buffers are declared DSP_YMEM.

FIR filter. A Finite Impulse Response filter computes each output as a weighted sum of the last N inputs: y[n] = h[0]x[n] + h[1]x[n−1] + … + h[N−1]x[n−N+1]. That is a dot product, N MACs per sample. The weights h decide what the filter does; the sketch designs a low-pass with the windowed-sinc method (once, in float) and converts the weights to Q15.

Goertzel. To find out how strong one frequency is in a block of samples, you do not need a whole FFT. The Goertzel algorithm is a tiny recursive filter tuned to that frequency; telephones use it to recognise the 8 DTMF tones of the keypad (each key = one row tone + one column tone).

How the code works

1. Q15 multiply with the compiler’s 16×16→32 multiply builtin:

inline q15 q15mul(q15 a, q15 b) { return (q15)(__builtin_mulss(a, b) >> 15); }

2. A dot product with the MAC builtin (any memory, about 10 cycles per element):

volatile register int acc asm("A");
acc = __builtin_clr();                                         /* A = 0 */
for (uint16_t i = 0; i < n; i++)
    acc = __builtin_mac(acc, x[i], y[i], 0, 0, 0, 0, 0, 0, 0, 0);   /* A += x*y */
return __builtin_sacr(acc, 0);                                 /* round, saturate, store */

3. The fast one: REPEAT + MAC with prefetch (dspDotFast()). CLR fetches the first pair; each MAC multiplies the pair fetched before and fetches the next one; REPEAT runs the next instruction n−1 times with no loop overhead:

"mov    %1, w8"                               /* x pointer, X bus */
"mov    %2, w10"                              /* y pointer, Y bus: must be in Y memory */
"sub    %3, #2, w0"
"clr    A, [w8]+=2, w4, [w10]+=2, w6"         /* A = 0, fetch x0, y0 */
"repeat w0"                                   /* next line n-1 times */
"mac    w4*w6, A, [w8]+=2, w4, [w10]+=2, w6"  /* A += x*y, fetch next */
"mac    w4*w6, A"                             /* last pair */
"sac.r  A, %0"                                /* round, saturate, store */

If the y buffer is not in Y memory, dspDotFast() falls back to the C version instead of trapping.

4. The FIR delay line trick (firRun()). Each input is written twice, at pos and pos + n, into a buffer of 2N samples. Then the last N inputs always form one straight block starting at pos, and one dot product with the coefficients gives the output, without any wrap-around test:

f.pos = (f.pos == 0) ? f.n - 1 : f.pos - 1;     /* newest sample goes "in front" */
f.x[f.pos] = in;
f.x[f.pos + f.n] = in;
return dspDotFast(f.h, &f.x[f.pos], f.n);       /* h[k] * x[n-k] */

5. RMS. The sum of squares of 256 samples is far larger than 1.0. The guard bits hold it (with SATA off, the default), and __builtin_sacd(acc, 7) stores it shifted right by 7 so it fits 32 bits.

6. Goertzel (in float, for clarity): s = x + 2cos(ω)·s1 − s2 for every sample, then the power from s1 and s2. Eight bins over 205 samples take about 11 ms at 100 MIPS.

In a power supply the output voltage is proportional to the duty: at 200 kHz with a 100 MHz clock one step is 0.2 % of the voltage, and a control loop that needs a value between two steps makes the output jump back and forth. An LED dimmed to 0.1 % brightness needs at least 1000 steps at the dark end, where the eye is most sensitive.

This chip has no true “high-resolution PWM”. The dsPIC33CK MP parts have a dedicated high-resolution mode with 250 ps edges; the core’s HRPWM library is for them. The MC005 on this board does not have that hardware. This lab gets the most out of what it has:
1. the fastest PWM clock: the generators can count at FVCO/2 = 400 MHz (nominal) instead of FCY = 100 MHz, so one step is 2.5 ns instead of 10 ns, 2 bits more at any frequency;
2. dithering: changing the duty by one tick on some periods, so the average moves in 1/16-tick steps (156 ps).

Six channels from three generators. Each generator PG1–PG3 drives two pins, H and L. Lab 16 used them as complementary pairs (L = not H, with dead time). Here they run in independent edge, dual output mode (MODSEL = 010, PMOD = independent): the H output rises at PGxPHASE and falls at PGxDC, the L output rises at PGxTRIGA and falls at PGxTRIGB. So every output has its own start and its own width. PG2 and PG3 start every period together with PG1 (SOCS = 1), so all six share one time base.

Dithering. Width 1000 ticks for 8 periods and 1001 for the next 8 averages 1000.5. How the code works

1. Clock and mode (pwm6Begin() and pwm6Frequency() in PWM6.h):

_PWMMD = 0;                                 /* power the PWM module */
PCLKCON = 0x0001;                           /* MCLKSEL = 01: FVCO / 2 */
*g.CONH   = (i == 0) ? 0x0000 : 0x0001;     /* PG2, PG3 start with PG1 (SOCS = 1) */
*g.IOCONH = IOCONH_PMOD_IND | IOCONH_PENH | IOCONH_PENL;   /* independent, PWM owns both pins */
*g.CONL   = CONL_CLK_MCLK | CONL_IND_DUAL;  /* master clock, MODSEL = 010 */
*g.PER    = ticks - 1;                      /* period = PER + 1 ticks */

Below 6.1 kHz the 16-bit period does not fit, so CLKSEL = 10 selects the clock divider and PCLKCON.DIVSEL sets 1:2 … 1:16. The generators are switched on in the order PG3, PG2, PG1, so the two followers are already waiting for PG1’s first period.

2. Writing one channel (pwm6Write()). Start and width in ticks become two edge registers; a falling edge past the end of the period wraps around. 0 % and 100 % use the override:

if (w == 0 || !pwm6Running) io = (io | ovrEn) & ~ovrHi;     /* hold low */
else if (w >= T)            io = io | ovrEn | ovrHi;        /* hold high */
else {
    uint16_t e = (s + w) % T;                               /* falling edge */
    if (L) { *g.TRIGA = s; *g.TRIGB = e; }
    else   { *g.PHASE = s; *g.DC = e; }
    io &= ~ovrEn;
}
*g.STAT |= STAT_UPDREQ;     /* load the new edges at the next period start */

UPDREQ makes the change glitch-free: the hardware copies the new values at the start of the next period, never in the middle of a pulse.

3. Dithering (_PWM1Interrupt, enabled only while a channel is dithered):

pwm6DitherAcc += pwm6DitherFrac;            /* 0..15 sixteenths per period */
uint16_t w = pwm6DitherBase;
if (pwm6DitherAcc >= 16) { pwm6DitherAcc -= 16; w++; }

4. Measuring (pwm6Measure()): PPS routes RB14 to SCCP2’s capture input (_ICM2R = 46), SCCP2 time-stamps 17 rising edges at FCY, and 16 periods give the frequency. pwm6Calibrate() then sets the clock to frequency × ticks per period.

Check your understanding

How many bits of resolution does a 100 kHz PWM have with a 400 MHz clock?

400 MHz / 100 kHz = 4000 ticks per period; log2(4000) = 12.0 bits.

How can three generators make six independent outputs?

In independent-edge dual-output mode each generator has two pairs of edge registers: PHASE/DC for the H pin and TRIGA/TRIGB for the L pin. All six share the period of their generator.

What does dithering give you, and what does it cost?

An average duty finer than one tick (1/16 tick here). The cost is a small ripple at the PWM frequency divided by 16, which the load or a filter must smooth out, and a little interrupt load.

Why does the sketch measure its own PWM frequency?

The PWM clock comes from the PLL’s VCO, whose exact value on this board is not yet confirmed. Measuring with SCCP2 (clocked from FCY) shows the real clock, and every ns value is corrected from it.

Background

What analogRead() hides. analogRead(A0) starts one conversion, waits for it, and returns 10 bits (0–1023), like a classic Arduino. The hardware gives 12 bits (0–4095) and can do much more without the CPU: start conversions from timers or PWM, convert many channels from one trigger, compare results with limits, and add results up for more resolution.

How the ADC is built. The MC005 has one 12-bit successive-approximation core (the “shared core”; the larger MP parts also have dedicated cores) behind a multiplexer with 22 inputs. What makes it powerful is that most settings exist once per channel:

Triggers. A conversion starts when the channel’s trigger source fires. The sources are: an individual software start (what adcRead() and analogRead() use), the common software trigger (one write starts every channel set to it), the level software trigger (converts again and again while it is on), PWM generator events, SCCP timers, CLC outputs and the PTG (Lab 33). A hardware trigger gives samples at exactly equal intervals, which a delay() loop never does.

Resolution and speed. With 12 bits and a 3.3 V reference one step (LSB) is 0.8 mV. 10, 8 and 6 bits are coarser but convert faster. The sample time is how long the input charges the ADC’s sample capacitor before the conversion: a high-resistance source (like a 10 kΩ pot) needs more of it.

Oversampling. Adding up 4 results and halving the sum gives one extra bit, if there is a little noise on the signal: 4× → 13 bit, 16× → 14 bit, 64× → 15 bit, 256× → 16 bit. The hardware filter does this by itself. In averaging mode it simply returns the mean of N results, which reduces noise and keeps 12 bits.

Formats. Integer results are right-aligned (0–4095). Fractional results are left-aligned in 16 bits, which suits Q15 math (Lab 36). Signed gives two’s complement around mid-scale, and differential measures the channel minus the negative input ANN0.

The band gap. AN21 is a fixed reference of about 1.2 V inside the chip. The ADC measures it relative to AVDD, so AVDD = 1.2 V × 4096 / result. The sketch uses this to correct all its millivolt values, without a voltmeter.

2. Per-channel registers by index. The trigger sources are one byte per channel, and the results one word per channel, both without gaps. So one pointer handles all 22 channels (checked against the linker script):

3. All channels from one trigger (adcScan()): set each channel’s trigger to “common software trigger”, write SWCTRG = 1 once, then collect the results as their ready bits come up. Reading ADCBUFx clears the ready bit.

4. Interrupts with a callback. adcAttachInterrupt(ch, fn) enables the channel in ADIEL/H and the common ADC interrupt. The interrupt calls fn(ch, value) for every ready channel. 5. Comparator and filter are configured by writing their registers: channel enable bits, limits and mode for the comparator, channel, ratio and mode for the filter. They then work on every result of that channel, with no code running.

6. Self-test of the timer trigger. The data sheet lists two SCCP3 trigger codes (SCCP3 = 22, SCCP3 Trigger = 14). findTimerPath() tries both for 30 ms, and if neither gives samples it falls back to the SCCP3 interrupt starting each conversion in software.

Check your understanding

Why does analogRead() return 0–1023 when the ADC has 12 bits?

For compatibility with classic Arduino sketches, which expect 10 bits. The core shifts the 12-bit result right by 2. adcRead() gives all 12 bits.

What is one LSB in millivolts at 12 and at 8 bits with AVDD = 3.3 V?

12 bit: 3300 / 4096 = 0.81 mV. 8 bit: 3300 / 256 = 12.9 mV.

Why is a timer trigger better than delay() between readings?

The hardware starts each conversion at exactly the same interval, no matter how long the rest of the program takes or whether interrupts are delayed. Equal intervals are required for filters and frequency analysis.

How does the band gap tell you the supply voltage?

The ADC measures every input as a fraction of AVDD. The band gap is a known 1.2 V, so its result gives the fraction 1.2 V / AVDD, and AVDD = 1.2 V × 4096 / result.
